现代代码审查中编码实践的 AI 辅助评估

作者：Manushree Vijayvergiya、Małgorzata Salawa、Ivan Budiselić、Dan Zheng、Pascal Lamblin、Marko Ivanković、Juanjo Carin、Mateusz Lewko、Jovan Andonov、Goran Petrović、Daniel Tarlow、Petros Maniatis、René Just（Google / 华盛顿大学）｜ 2024 年 7 月，巴西 Porto de Galinhas

摘要

现代代码审查（code review）是指：由一名或多名同行，在代码贡献被提交到版本控制系统之前对其进行审查的过程。现代代码审查的一个重要环节，是核对该代码贡献是否遵循最佳实践。虽然其中一部分最佳实践可以被自动验证，但其余的通常由人工审查者负责核验。本文报告了 AutoCommenter 的研发、部署与评估——这是一个由大语言模型（LLM）支撑、能够自动学习并强制执行编码最佳实践的系系统。我们针对四种编程语言（C++、Java、Python、Go）实现了 AutoCommenter，并在一个大型工业环境中评估了它的性能与采用情况。我们的评估表明：一个用于学习并强制执行编码最佳实践的端到端系统是可行的，并且对开发者工作流有积极影响。此外，本文还报告了将该类系统部署到数万名开发者时所面临的挑战，以及相应的经验教训。

1 引言

现代代码审查（相较于整体式代码审查）多年来在开源与工业环境中自然演化而成。一系列常见的同行评审标准已经浮现，其中包括编码最佳实践。许多公司、项目乃至编程语言，都以"风格指南"（style guides）的形式正式定义它们，通常涵盖以下方面：

  • 格式化（Formatting）：行宽限制、空格与缩进的使用、括号与方括号的位置等；
  • 命名（Naming）：大小写、简洁性、描述性等；
  • 文档（Documentation）：文件级、函数级及其他注释的期望位置与内容；
  • 语言特性（Language features）：在不同（代码）语境下对特定语言特性的使用；
  • 代码惯用法（Code idioms）：使用代码惯用法来提升代码的清晰度、模块化与可维护性。

开发者普遍对现代代码审查流程表示高度满意。其主要好处之一，是让不熟悉代码库、特定语言特性或常见代码惯用法的代码作者获得学习体验。在审查过程中，资深开发者除了审查（并了解）代码贡献及其影响外，还会就最佳实践对代码作者进行指教。

诸如 linter（代码检查器）之类的静态分析工具，可以自动验证代码是否遵循某些最佳实践（例如格式化规则），有些工具甚至能自动修复违规。然而，那些带有细微差别、或存在例外的准则，很难被完整自动验证（例如命名规范，以及在遗留代码中有理有据的偏离）；而有些准则根本无法被精确的规则所捕获（例如代码注释的清晰度与具体性），只能依赖人工判断与开发者群体的集体知识。

因此，通常期望人工审查者检查代码变更是否存在最佳实践违规。代码审查流程最大的成本，是所需的时间，尤其是资深开发者的时间。即便已有大量自动化、并尽量让流程保持轻量，一名开发者每天也很容易在这项任务上投入数小时。

机器学习的最新进展，尤其是大语言模型（LLM）的能力，表明 LLM 适合用于代码审查自动化。然而，围绕"在规模上部署端到端系统"的软件工程挑战仍未被探索；同样，这类系统在整体效能与用户接受度方面的外部评估也尚属空白。

本文研究是否有可能部分自动化代码审查流程，特别是对"最佳实践违规"的检测，从而为代码作者提供及时的反馈，并让审查者把注意力放在整体功能上。具体而言，本文报告了我们在 Google 这一工业环境中研发、部署并评估 AutoCommenter（一个自动化代码审查助手）的经验，它目前每天被数万名开发者使用。

总之，本文的贡献包括：

  • 一个基于 LLM 的代码审查助手系统的通用架构（第 3 节）；
  • 工具校准与向数万名开发者部署的描述（第 4 节）；
  • 对系统的评估（第 5 节）；
  • 经验教训的总结与讨论（第 6 节）。

2 背景

AutoCommenter 是在 Google 的大型工业环境中研发的。Google 的现代代码审查实践与其他工业和开源项目类似。

2.1 代码审查流程

Google 的代码审查流程成熟、基于变更（change-based）、并由工具辅助。每位对代码库的变更都必须至少由另一名开发者审查。每天，代码库有数万次变更经过审查流程，并有数万名开发者以代码作者和审查者的双重身份参与其中。

作者与审查者通过代码审查系统交换评论，审查随"受变更影响的文件的快照"逐步推进。每条审查评论都附加在某个具体文件快照的某一行与某一列范围上。要解决一条评论，作者通常会在本地副本中修改文件，并导出新的快照进入下一轮审查。当作者与所有审查者都满意、且没有自动化分析阻塞合入时，代码便被合入代码库。

代码审查流程中最昂贵的部分，是代码作者与审查者"护送"一次变更所花的时间（从初始编码，到处理审查评论、确保所有自动化分析通过，再到最终合入代码库）。尽管该流程已用自动化系统在审查前分析代码（ notably 无需人工干预的自动代码格式化）进行了优化，代码审查每年仍要耗费数千"开发者年"。因此，即便个位数的百分比节省，也能转化为显著的商业影响。

2.2 最佳实践

最佳实践是指某种被认为更优的编程语言用法；而最佳实践文档描述了应如何应用它、以及它带来什么好处。"最佳实践 URL"指一份最佳实践文档或其内部某个具体小节；"最佳实践违规"指一段不符合某最佳实践、但可以被修改以符合的代码。如果上下文清楚，我们用术语"URL"和"违规"分别指代最佳实践 URL 与最佳实践违规。

Google 的中央代码仓库包含多种语言，其中 C++、Java、Python、Go 各自超过 1 亿行代码。对于 15 种不同的语言，都有正式的风格指南对所有开发者开放。许多语言还有额外的语言入门、核心库文档，以及"本周提示"式的简报。虽然这些材料不如风格指南那样被严格执行，但在代码审查中经常被引用。有些语言的这类文档多达数百页。代码作者与审查者都被期望核验代码是否遵循了所有最佳实践。

一个十多年前引入的正式机制——"readability"（可读性），确保最佳实践被一致遵循。某一语言中专门的风格专家，被称为"readability mentors"（可读性导师），引导缺乏经验的开发者走向对该语言的精通。可读性导师通常会用几句话总结一条最佳实践，并在评论末尾附上一个 URL 供变更作者参考。

可读性流程也有一些缺点。对作者而言，额外的审查轮次增加了开发时间。对可读性导师而言，这可能成为单调且耗时的任务——它需要掌握数百条不断演进的最佳实践，包括识别并弃用过时的规则，并在代码审查系统中（附上相关链接）记录它们；此外还需要追踪、有时要跨多轮迭代，确保所有违规都已被修复。

3 方法

针对第 2.1 与 2.2 节描述的挑战，我们研发了 AutoCommenter——一个能自动检测最佳实践违规的代码分析工具。它旨在为代码作者提供及时反馈，并减轻人工最佳实践审查的需要，从而让审查者聚焦于代码功能。

3.1 模型与任务定义

自动化最佳实践分析，需要一个能表示源代码、定位违规位置、并识别被违反的最佳实践的模型。我们针对一个多任务大序列模型中的一个任务，采用基于 T5 的传统 transformer 方法（使用 T5X），进行"文本到文本"的转换。除了 T5 的标准预训练任务（span denoising，预测被掩码的词）之外，用于训练该模型的其他任务还包括：代码审查评论解决、下一次编辑预测、变量重命名，以及构建错误修复。

训练语料包含超过 30 亿条样本，其中最佳实践分析数据集贡献了约 80 万条。模型使用此类模型典型的标准交叉熵损失进行训练，并调优以最大化序列准确率指标——即对每个样本精确预测目标文本。

对最佳实践分析而言，模型的输入是一个任务提示（task prompt）与源代码，目标是一段源代码的位置，以及一条指向被违反的最佳实践的 URL。任务提示被格式化为一段固定文本的代码注释，采用该编程语言合适的注释风格；它用自然语言描述任务，并位于源代码之前——源代码是某个文件的直接文本表示。如果输入超出模型的上下文窗口，会被截断。位置是源代码中的一个字节偏移量，URL 指向被违反的最佳实践。一个领域特定的语言定义了目标格式；特殊情况是"空"目标——当没有任何违规时。除目标外，模型还会输出一个 0 到 1 之间的置信度分数。

考虑以下 Go 语言的输入/目标示例：

输入

// [*] Task: Check language best practices.
// Package addition provides Add
package addition
// Return a sum
func Add(value1, value2 int) int {
  return value1 + value2
}

目标

INSERT 153 COMMENT https://go.dev/doc/comment#func

输入的第一行是固定文本的任务提示；其余是源代码。目标给出了位置（字节偏移量 153 对应 Add 函数的起始处）和一个 go.dev 的 URL，指向 Go 语言风格指南中该函数注释所违反的确切部分（在本例中，是用函数名开头注释的惯例）。注意，目标可能包含零个、一个或多个（拼接的）"位置-URL"对，取决于源代码中违规的数量。

3.2 模型训练

图 2 展示了模型训练管线的架构，它由三部分组成。我们将数据集创建拆成两步（预处理与策展），因为第一步要在大得多的数据量上运行，成本高得多。预处理步骤的输出与模型的输入/目标表示无关。这种分离通过让我们能快速迭代样本表示及其他样本级调整，提升了特性迭代速度。预处理步骤使用一个容错的调度系统，并周期性地抽取相关的代码注释，以确保新数据随时可用。

3.2.1 大规模预处理

训练样本来自真实的代码审查数据，但并非所有代码评论都适合用于模型训练。因此，预处理步骤会识别相关的代码评论——即那些包含指向最佳实践文档的 URL 的人工撰写评论。对每条评论，预处理步骤接着收集相应的源代码及相关的元数据，包括该评论在源代码中的位置，以及它的创建时间。这一步的输出是一组相关的代码评论，每条都带有为模型训练策展样本所需的全部数据。

3.2.2 数据集策展

数据集策展是一个按需执行的单一步骤，实现为一个 Beam 管线。它基于第 3.1 节描述的输入/目标格式，把每条相关的代码评论转换成标准的 TensorFlow Example 数据结构。

3.2.3 训练与微调

策展后的样本被直接用于模型训练与评估。我们在 TPU 集群上使用 T5X 框架，每 1000 步保存一次模型检查点，并用 Tensorboard 监控训练。

3.3 模型选择

对历史数据的两次内在评估，为我们的模型检查点、置信度阈值与解码策略的选择提供了依据。首先，在验证集与测试集上的评估，提供了按文件计的精确率与召回率的估计。其次，在完整历史代码审查上的评估，提供了每次代码审查的评论总数的估计，指示开发者会与 AutoCommenter 交互的频繁程度。

3.3.1 验证集与测试集上的评估

我们对数据集做时间切分，以确保模型没有在验证集与测试集所含代码评论的"未来"代码审查快照上训练过。在我们的数据集中，85% 的文件恰好只有一条相关代码评论，11% 有两条，4% 有三条或更多。我们定义：只要预测的代码位置与 URL 与期望值匹配（不论顺序），该预测即为正确。

回想一下，模型为每次预测提供一个置信度分数，这引入了另一个参数：如果某预测的置信度分数低于某个阈值 t，它可以被抑制。我们定义 Precision_t 为"置信度大于 t 的正确预测数"除以"置信度大于 t 的所有预测数"；Recall_t 类似定义。这些定义让我们能估计——作为 t 的函数——会有多少（不）正确结果展示给用户。Precision_t 与 Recall_t 用于训练期间的模型检查点比较。

虽然这一评估避免了数据泄漏，并让我们能自动评估模型性能，但它有一个局限：我们有理由假设，给定代码审查快照的人工评论是正确的，但它们并不 exhaustive（穷尽）。换句话说，某个代码审查快照中的代码，可能可以按照多条最佳实践来改进，但人工审查者并没有为它们全部张贴（带 URL 的）评论。这可能出于若干原因：

  • 缺失引用：审查者可能对某个问题发表了评论，但没有附带 URL 作为参考。
  • 选择性评论：审查者可能对某个问题只评论一次，期望作者通篇应用修复。
  • 专业度或关注点不同：审查者可能并不熟悉所有最佳实践，或者只是选择不在某次代码审查的语境下评论某个问题（例如只关注被改动的代码）。

虽然我们数据集中大多数文件只有一条相关评论，但基于手工检视"不正确"预测的轶事证据表明：由于上述原因，多条最佳实践评论通常是可能的。鉴于我们的真值数据不完整，精确率与召回率的度量是有噪声的。因此，我们采用了下一节描述的补充评估，以增强对整体模型性能的把握。

3.3.2 完整历史代码审查上的评估

为了准确衡量实时环境中的潜在评论量，我们在一组历史代码审查上评估 AutoCommenter，使用特定的模型检查点与阈值。预测的评论不会 retroactively（回溯地）张贴到代码审查系统中，而是记录到数据库供分析。这让我们能估计预期的张贴频率——既有按文件的粒度，也有按代码审查的粒度。由于开发者是在一整批待审查的代码变更上与 AutoCommenter 交互，这一步是生产部署前的重要步骤。作为一项额外好处，这一步也允许针对不同用户群体、编程语言等做进一步优化，并评估张贴频率。

3.4 推理基础设施

AutoCommenter 的核心是一个中央最佳实践分析服务。该服务把一个或多个待分析的源文件作为输入。对每个文件，它构造一个模型输入（第 3.1 节），用标准的 TensorFlow Example 数据结构编码，并查询模型。模型本身由一个模型服务托管，该服务使用 TensorFlow 的 Example 数据结构作为领域无关的輸入输出格式。最后，最佳实践分析服务执行一系列过滤步骤（第 4 节），抑制低质量的预测，并返回剩余的预测。

3.5 IDE 与代码审查集成

开发者以两种方式与 AutoCommenter 的分析服务交互——直接通过 IDE 插件，或间接通过代码审查系统。代码审查系统被 Google 的所有开发者使用，IDE 则被几乎所有人使用。

AutoCommenter 的评论在 IDE 中以诊断信息的形式出现，带有蓝色波浪下划线，覆盖相关的代码片段。悬停在被下划线的代码上，会显示完整的评论，包括对最佳实践的简洁总结，以及指向相关最佳实践文档的可点击链接。这种内嵌信息通过消除"在 IDE 与浏览器间切换以查阅不熟悉的最佳实践"的需要，简化了开发者的工作流。由于 IDE 中的评论需要实时生成，我们的目标是以亚秒级延迟生成评论。

在代码审查系统中，AutoCommenter 在每次更新（即每个新的代码审查快照）后运行，一旦检测到任何违规就自动张贴评论。自动化工具产生的评论在视觉上类似于人工产生的评论，但背景色不同。图 3 展示了 AutoCommenter 在代码审查系统中生成并张贴的一条评论示例。注意右侧的点赞与点踩按钮（开发者若觉得某条评论特别有用或没用，可点击），以及左侧的"Please fix"（请修复）按钮（审查者可见）。如果点击它，会生成一条新评论，表明该审查者认为这条评论很重要、必须在合入前处理。这些反馈按钮在代码审查系统中是标准的，出现在所有自动化工具生成的评论上，并提供一个工具用户接受度的信号。IDE 提供了类似的反馈机制。

4 部署

我们在 2022 年 7 月到 2023 年 10 月期间，分阶段将 AutoCommenter 部署给 Google 的所有开发者：

  • 至 2022 年 7 月——团队内测（teamfooding）：本文作者。
  • 2022 年 7 月——早期采用者：约 3000 名志愿者。
  • 2023 年 7 月——A/B 实验：约一半开发者。
  • 自 2023 年 10 月——全面可用（general availability）：所有开发者。

出于工业保密原因，我们无法披露代码审查、开发者、文件、评论的绝对数量，或代码审查时长的分布。我们在适当时报告相对度量与相关趋势。

我们使用迭代式精炼方法，持续评估并改进 AutoCommenter 的性能：

  • 在历史数据上的评估（第 3.3 节），以获得模型在该任务上表现的方向性洞察，并定义阈值、选择解码策略。
  • 监控与分析用户交互，以及通过反馈按钮与问题报告得到的直接反馈。
  • 基于其他评估步骤中观察到的模式，做有针对性的用户评估。

图 4 展示了所张贴代码审查评论与 IDE 诊断信息中，开发者正面与负面反馈之比随时间的变化。虚线展示了开发者每月提供的反馈点击总数。如预期，早期采用者阶段的计数低得多；此外该阶段波动更大，因为我们在 actively 精炼 AutoCommenter。回想代码审查系统中的三个反馈按钮（图 3），开发者可借其对所张贴评论表达正面或负面情绪。我们将带点赞或"Please fix"的评论视为正面，带点踩的评论视为负面；我们将"有用比"（useful ratio）定义为正面评论占所有有反馈评论的比例。

本节剩余部分描述我们在部署期间所做的具体观察及相应的精炼。

4.1 选择阈值与解码策略

4.1.1 阈值

在初始部署时，我们想谨慎管理开发者对 AutoCommenter 的信任，于是从一个很高的置信度阈值 t=0.98 起步。我们手工抽样了数百条结果，观察到阈值以下的预测中约 80% 仍然正确——也就是说，在 t=0.98 时假阴性率非常高。此外，我们观察到 Python 的预测置信度分数分布显著不同，受阈值化的影响不成比例。我们推测，训练数据集的构成（不同 URL 的数量与 URL 频率）以及最佳实践文档的具体性是其原因，但把更深入的调查留待未来工作。尝试部署"按语言"的阈值被证明无效——单一的语言级阈值仍不足以充分刻画模型正确预测数百种多样化最佳实践的能力。这导致预测的 URL 缺乏多样性，因为模型倾向于对某些 URL 给出更高的分数，而非其他 URL，无论正确与否。这些观察促成了 AutoCommenter 的第一个重大改动：基于验证集内在评估计算出的"按 URL"阈值。

4.1.2 解码

使用"按 URL 阈值 + 贪心解码"在完整历史代码审查上的评估显示：AutoCommenter 在所有被改文件中检测到 6% 存在违规。然而，80% 的评论本会被张贴在作者未修改的代码行上。开发者通常不会对未更改的代码采取行动。因此，AutoCommenter 过滤掉针对未更改代码行的生成评论，将被改文件中的评论占比降至 1.3%。为了提高这一比例，我们尝试了不同的解码策略：贪心（默认）、beam search、top-k 与 top-p 采样。我们最终选择了 beam search（生成 n=4 个潜在响应），它将张贴频率提升至 3.9%，同时也带来了显著更高的 URL 多样性：被张贴最多的 10 个 URL 占所有评论的 41%，而贪心解码下为 80%。

延迟是选择部署解码策略时的另一个重要方面。虽然 beam search 提高了张贴频率与多样性，推理也明显变慢（中位延迟 2 秒）。鉴于该延迟对 IDE 中的交互式使用是不可接受的，我们最终决定：代码审查系统使用 beam search，IDE 使用贪心搜索。

4.2 抑制过时的最佳实践

在将 AutoCommenter 推向约 3000 名自愿的早期采用者后几天内，我们注意到用户提交了大量 issue。其中许多对应于同一个 URL，它描述了与 Python imports 相关的最佳实践。然而，某些类型名的正典来源在 Python 3.9 中已更改，该最佳实践也在 2022 年初发生了变化。由于我们的训练数据延伸到 2022 年之前，它包含了一些不再适用的最佳实践评论。我们意识到这是一种反复出现的模式：随着语言演进或新库引入，最佳实践也会演进。缓解这一问题的方法之一，是过滤掉此类数据（每当某条规则变化时）并重新训练模型。但这既耗时又耗资源：它需要完整的数据再生、模型训练、评估与发布。在此期间，"过时"的模型要么被关闭（导致系统停机），要么相关预测需要被抑制——否则系统会迅速失去开发者的信任。我们选择了抑制特定的最佳实践预测，使用条件过滤（在源代码上匹配正则表达式），原因有二：首先，它可以动态部署并立即生效；其次，它允许对预测做细粒度过滤。

4.3 对精选评论的独立评分

在数月的早期使用后，我们观察到有用比在约 54% 处进入平台期。为了理解原因、找出改进空间并为更广泛部署做准备，我们在 2023 年 4 月开展了一项独立的人工评分研究，分析了约 370 条在早期采用者部署期间收到开发者反馈的已张贴评论样本。

为收集关于评论有用性的多元视角，我们招募了 15 名评分者——来自合作团队的开发者。我们要求他们对收到过明确用户反馈的 AutoCommenter 评论进行评分。我们没有向评分者展示原始的用户反馈，以避免使其评估产生偏差。评分者基于所链接的最佳实践与周边代码，评估每条评论的有用性。我们指示他们聚焦于评论的正确性，以及这条评论对作为作者的他们而言是否"可操作"（例如，他们是否会去解决一条技术上正确、但在某个具体实例中似乎不值得解决的评论）。我们鼓励他们针对每条评论提供自由形式的反馈。

评分者评估得到的有用比为 60%，略高于同一批评论上开发者反馈的 54%，但远低于我们为更广泛部署设定的 80% 目标。本研究最有趣的发现是：存在清晰的"无用评论"模式。以下是一些例子：

  • 多个主题或复杂主题：例如，有一个 URL 指向描述与 Python linter 交互的多条准则的小节，包括它经常触发的情形以及抑制它的方法。作者可能难以理解所张贴评论指的是哪条具体准则、以及如何解决它。类似地，C++ 中关于写好函数文档的指南是一整页密集文本。评分者频繁指出：即便存在相关违规，最佳实践（与 AutoCommenter 的简洁总结）与实际代码之间也存在脱节。
  • 高质量总结的重要性：评分者经常发现，AutoCommenter 的总结（通过抓取文档来源生成，有时缺失）未能充分解释所引用准则与评论/代码的相关性。
  • 主观且可能引发争议的的主题：一个例子是避免在库代码中使用 flag。flag 在库中使用时会导致问题，但有些库正是被设计为可通过 flag 配置许多特性。此外，遗留代码可能不遵循该准则，审查者也不会强制执行它。模型没有学到这些细微差别，有时会在作者向现有库添加新 flag 时预测出违规。
  • 某些准则的系统性模型错误：一个有趣的例子是，一条准则提倡：当 C++ vector 的 push_back 与 emplace_back 都能用相同参数达到相同效果时，优先使用成员函数 push_back。模型学到了预测这一点，但它也会在 emplace_back 更合适的情况下预测它，也会在某个不相关的类型拥有一个名为 push_back 的成员函数时预测它。
  • 正确但低价值的评论：代码注释末尾缺少一个句号，通常被人工审查者允许。虽然技术上正确，但让作者回到 IDE 去修复该问题，可能带来净负价值。

评分研究的洞察促成了 AutoCommenter 的两项改动。首先，评分研究识别了 17 个"不可操作"的 URL，抑制它们使历史有用比从开发者反馈的 54% 提升到 66%，从评分者反馈的 60% 提升到 74%。我们进一步分析了链接到类似、未评分 URL 的评论，又抑制了额外的 5 个。其次，我们审查并手工更新了所有被频繁张贴的 URL 的总结。这些改动合在一起，足以让我们在下一部署阶段达到 80% 的有用比目标。

4.4 A/B 实验

2023 年 7 月，我们在 A/B 实验的语境下，将 AutoCommenter 部署给约一半开发者。我们随机将开发者分配到实验组（启用 AutoCommenter）与对照组（禁用 AutoCommenter）。我们基于开发者邮箱地址 SHA256 哈希的最后几位做随机化，并验证了两组在规模与构成（包括任期、资历、编程语言与业务部门的分布）上没有差异。我们也确认：在实验开始前，实验期间测量的任何变量在对照组与实验组之间都没有差异。实验期间的评论张贴频率与预期一致（第 4.1 节）。

我们未检测到以下任何一项有统计显著的变化：代码审查总时长、开发者主动花在代码审查上的时间、作者与审查者之间评论-回复的迭代次数。但我们确实检测到了编码速度上轻微的改善。我们推测：减少切换到文档的上下文切换，带来了这一正面效果。我们把更深入的调查留待未来工作。

基于这些结果，我们得出结论：没有不良影响，并于 2023 年 10 月将 AutoCommenter 部署给所有开发者。

5 评估

基于自 2023 年 3 月以来收集的有用比与用户反馈，我们得出结论：开发者总体上对 AutoCommenter 产生的评论是满意的。我们通过分析用户反馈，持续精炼我们的数据集准备、阈值、URL 抑制与总结，以确保 AutoCommenter 对开发者工作流带来高度正面影响。

除了开发者满意度，在面向全 Google 广泛发布数月后，我们评估了 AutoCommenter 性能的另外三个方面：

  • （1）评论解决率：开发者修改自己代码的频率有多高，以解决 AutoCommenter 张贴的评论？
  • （2）AutoCommenter 对比人工评论：AutoCommenter 的评论在覆盖"人工审查者在其评论中引用的"最佳实践文档方面表现如何？
  • （3）AutoCommenter 对比 linter：AutoCommenter 的输出在多大程度上超越了传统静态分析工具的能力？

5.1 评论解决率

开发者很少通过点击代码审查系统与 IDE 中的点赞/点踩按钮、以及代码审查系统中的"Please fix"按钮（图 3），对 AutoCommenter 的评论给出明确反馈：代码审查系统中约 10% 的自动化评论、IDE 中约 2% 的诊断信息收到了明确反馈，这与 Google 的其他自动化分析相当。与此同时，开发者悬停在约 50% 的 AutoCommenter IDE 诊断信息上；先前的工作表明开发者常常在没有任何明确反馈的情况下解决自动化评论。为评估开发者解决 AutoCommenter 评论的频率，我们做了一项离线分析，估计由后续代码变更解决的评论比例。

为分析评论解决率，我们提取了聚焦在"带有 AutoCommenter 自动化评论的文件"上的历史变更。对每条，我们提取了评论被张贴时的初始快照，以及开发者最终合入代码库的快照。每条评论跨越一个具体的行范围。我们使用了一种基于 AST 的自动化行映射方法（文献 [18]）在这两个快照之间做映射，以识别那些模型在第一个快照上预测、但在合入快照上不再预测的评论。这样的快照对表明某条评论可能已被解决，但也可能由于不相关的代码变更导致某条特定评论不再被预测。

对 6000 个快照对的自动化分析显示：在 50% 的情况下，评论在其被初始张贴的行上，从提交的快照中消失了。我们对其中 40 个此类快照对做了随机手工检视。我们发现：在 80% 的情况下，作者做出的某个变更直接解决了所张贴评论描述的问题。因此，我们估计评论解决率约为 40%，这显著大于"带有明确正面反馈的评论占所有评论的比例"。

5.2 AutoCommenter 对比人工评论

图 5 比较了：AutoCommenter 在生产中生成的自动化评论，与训练数据中人工评论，各自"按唯一 URL（指向最佳实践文档）计"的累积分布。x 轴是 URL 的排名——当所有曾在自动化评论中使用过的 URL 按频率排序时。例如，被使用最频繁的 URL 排名为 1，它占所有自动化评论的 9.9%；同一 URL 出现在训练数据中 4.3% 的人工评论里。总计，AutoCommenter 为 330 个不同的 URL 创建过评论。AutoCommenter 使用的 URL 集合覆盖了历史人工评论中带最佳实践 URL 的 68%。这是一个好结果：它表明 AutoCommenter 没有聚焦于审查者很少引用的冷门最佳实践。另一方面，尽管使用了 beam search，URL 多样性仍然相对较低——排名前 85 的 URL 占据了 AutoCommenter 所创建评论的 90%；同一组 URL 覆盖了带最佳实践 URL 的人工评论的 35%。在保持准确率与低延迟的同时，提升自动化评论中最佳实践的 URL 多样性与覆盖率，是我们的首要任务之一。

5.3 AutoCommenter 对比 Linter

为理解 AutoCommenter 在多大程度上提供了超越"能高效、精确检查部分最佳实践的 linter"的价值，我们抽样了被预测最频繁的 50 条违规——即图 5 中排名前 50 的 URL。对每个抽样的 URL，我们检视其最佳实践文档，并判定（1）最佳实践类型（第 1 节），以及（2）是否存在、或是否能轻易构建一个检测相应违规的 linter。具体而言，三位作者（各自有超过 10 年构建静态分析工具的经验）阅读文档并独立对 URL 分类。在最佳实践类型上没有分歧，但在"是否能轻易构建 linter"上，约 15% 的 URL 存在分歧。三位作者通过多数投票与讨论解决了这些分歧。分歧源于模糊的最佳实践，以及那些包含多条准则的实践。例如，检查代码文档是否存在相对直接，但推理"有理有据的例外"与"内容的清晰度"则可能并不容易。

图 6 展示了这 50 个抽样 URL 的分布，按类型以及"违规是否可被 linter 检测"细分。对于其中 33/50（66%）的最佳实践，违规检测超出了传统静态分析的范围。

6 经验教训

基于研发并部署 AutoCommenter 的经验，我们总结了若干关键教训：

  • 补充传统分析：AutoCommenter 的 LLM 支撑方法，为人工审查者频繁引用的 68% 最佳实践生成了评论；其中许多超出了传统静态分析的范围。
  • 内在评估 vs. 真实世界性能：内在评估与真实世界性能可能显著背离——我们的内在评估，使用真实世界人工评论的数据集，配合最先进的模型架构与训练流程，显示了一个有前景的模型；但我们的外部评估与系统改进，对成功部署而言至关重要。
  • 监控用户接受度至关重要：即便少数负面的用户体验，也会侵蚀对自动化系统的信任。持续监控并分析真实世界反馈，对于检测此类情况并找出补救办法至关重要。在 AutoCommenter 的案例中，一个简单的抑制机制，就足以在不显著牺牲效能的前提下，将用户接受度强力提升到 80% 以上。

7 相关工作

Johnson 在约 50 年前的 1977 年引入了 C linter。在那 50 年里，产生了大量关于自动化静态分析的研究：Heckman 与 Williams 近期的一篇文献综述识别出了 17,571 篇论文。许多研究探索开发者如何与静态分析交互。Johnson 等人探索开发者在尝试使用静态分析时面临的挑战，其研究结果突出了：良好集成到现有开发者工作流中、以及培养并维持对该工具的信任的重要性。Vassallo 等人在不同语境（包括编码与代码审查）下探索开发者如何与静态分析交互；他们也发现：集成到现有工作流中，在开发者使用这些工具的意愿上起着主要作用，且结果的高质量极为重要。Beller 等人在大量开源项目中研究了静态代码分析的使用，并指出：自动化分析如何被使用、以及应当如何被使用，会因编程语言而异。

相比之下，用机器学习做代码分析是一个相对新颖、且理解较少的领域。一些近期的发表（例如 Hong 等人、Li 等人、Thongtanunam 等人、Tufano 等人）报告了模型评估并提出了自动化代码审查的工具。虽然这些模型与"评论生成"任务和本文模型非常相似，但评估主要聚焦于历史数据集。正如第 3.3.1 节所讨论的，仅基于历史评论的内在评估有一定局限，有时无法预测真实世界性能。另一篇由 Frömmgen 等人发表的近期论文，呈现了对一个实时系统的评估，但针对的是相反的任务：从评论创建代码，而非从代码创建评论。

8 结论

核验代码是否遵循最佳实践，是现代代码审查流程中的常见任务。虽然部分最佳实践可以用 linter 等传统工具自动验证，许多仍需要资深开发者的知识与判断，而这需要时间与精力。

本文报告了我们研发、部署并评估 AutoCommenter——一个 LLM 支撑的代码审查助手系统——的经验。具体而言，它铺陈了从任务与模型设计、经内在评估与系统校准、到分阶段推出与终端用户评估的完整过程。

评估结果表明：开发一个端到端系统、其能力远超传统工具、同时达到高度终端用户接受度，是可行的。这些结果朝部署复杂的代码审查助手与自动化代码审查，迈出了有前景的第一步。

我们的首要任务是：通过把 AutoCommenter 设计为"极高精确率"，来确保正面的开发者体验。虽然召回率并非主要关注点，我们承认它的重要性，并计划探索模型与系统架构上的哪些改动可以提升召回率。例如，我们 2022 年使用的模型在当时是最先进的，但它有限的 2048 token 上下文窗口，只够约 200 行代码。当前最先进的模型在训练时拥有数万 token 的上下文窗口，在推理时则超过一百万 token。这一跃迁为新的特性、以及对现有特性的显著改进，打开了机遇。
