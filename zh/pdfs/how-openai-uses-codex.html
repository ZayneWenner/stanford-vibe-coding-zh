OpenAI 如何使用 Codex

引言

Codex 在 OpenAI 的众多技术团队中每日被使用，包括安全、产品工程、前端、API、基础设施与性能工程等团队。各团队正在用它加速一系列工程任务——从理解复杂系统、重构大型代码库，到交付新功能、在紧迫期限内处置事故。

基于与 OpenAI 工程师的访谈以及内部使用数据，我们整理出这些用例与最佳实践，它们凸显了 Codex 如何帮助我们的团队跑得更快、提升工作质量，并在规模上管理复杂性。

用例 1：代码理解

在新人上手、调试或调查事故时，Codex 帮助我们的团队快速熟悉代码库中不熟悉的部分。他们常常用 Codex 定位某个功能的核心逻辑、梳理服务或模块之间的关系，并追踪数据在系统中的流转。它还能揭示架构模式，或那些本需要大量人工才能生成的、缺失的文档片段。

在事故响应期间，Codex 通过揭示组件之间的交互、或追踪失败状态如何在系统中传播，帮助工程师快速进入新领域。

团队轶事
  • "我修 bug 时，用 Ask 模式查看代码库中同样的问题还可能出现在哪里。"——检索系统，性能工程师
  • "我值班时，把堆栈跟踪贴给 Codex，问它鉴权流程在哪。它直接跳到正确的文件，让我能快速分诊。"——API 平台，站点可靠性工程师（SRE）
  • "Codex 回答我在 Terraform 和 Python 上'这种改动该在哪里做'的仓库问题，比 grep 快多了。"——基础设施服务，DevOps 工程师

用以下示例 prompt 试试把 Codex 用于代码理解：

Where is the authentication logic implemented in this repo?
Summarize how requests flow through this service from entrypoint to response.
Which modules interact with [insert module name] and how are failures handled?

用例 2：重构与迁移

Codex 常被用于做出跨越多个文件或包的改动。例如，当工程师更新一个 API、改变某个模式的实现方式，或迁移到新的依赖时，Codex 让一致地应用改动变得轻松。

当同一个更新需要在数十个文件中应用时，或者当该更新需要感知结构与依赖、而无法被正则或查找替换轻易捕获时，它尤其有用。

他们也在代码清理中使用它——拆分过大的模块、用现代模式替换旧模式，或为更好的可测试性准备代码。

团队轶事
  • "Codex 把我们所有的旧 getUserById() 换成了新服务模式，并开了 PR。它几分钟就做完了原本要数小时的事。"——ChatGPT Web，后端工程师
  • "为了清除发布阻塞，我让 Codex 扫描旧模式的每个实例，用 Markdown 总结影响，然后开带修复的 PR。"——ChatGPT Enterprise，产品工程师

用以下示例 prompt 试试把 Codex 用于重构与迁移：

Split this file into separate modules by concern and generate tests for each one.
Convert all callback-based database access to async/await.

用例 3：性能优化

Codex 被用于识别并处理性能瓶颈。在调优或可靠性工作中，工程师提示 Codex 分析缓慢或内存密集的代码路径——例如低效循环、冗余操作，或代价高昂的查询——并提出优化替代方案，常常带来效率与可靠性上的可观收益。

Codex 也被用于支持代码健康：识别仍在活跃使用的、有风险或被弃用的模式。我们的团队依靠它来减少长期技术债，并主动防止回归。

团队轶事
  • "我用 Codex 扫描重复的、代价高昂的 DB 调用。它很擅长标记热点路径，并起草我可以稍后调优的批量查询。"——API 可靠性，基础设施工程师
  • "Codex 很擅长快速发现性能问题——我花 5 分钟写 prompt，省下了 30 分钟的工作。"——模型服务，平台工程师

用以下示例 prompt 试试把 Codex 用于性能优化：

Optimize this loop for memory efficiency and explain why your version is faster.
Find repeated expensive operations in this request handler and suggest caching opportunities.
Suggest a faster way to batch DB queries in this function.

用例 4：提升测试覆盖率

Codex 帮助工程师更快地编写测试——尤其是在覆盖薄弱或完全缺失的地方。在处理 bug 修复或重构时，工程师常让 Codex 建议覆盖边界情形或可能失败路径的测试。对新代码，它可以基于函数签名与周边逻辑生成单元测试或集成测试。

Codex 在识别边界条件上特别有帮助——例如空输入、最大长度，或不寻常但有效的状态——这些常常在最初的测试中被遗漏。

团队轶事
  • "我让 Codex 在夜间指向低覆盖率的模块，醒来就看到可运行的单元测试 PR。"——ChatGPT Desktop，前端工程师
  • "当切换单仓库分支很痛苦时，我让 Codex 写测试并启动 CI，而我继续在我自己的分支上工作。"——支付与计费，后端工程师

用以下示例 prompt 试试把 Codex 用于提升测试覆盖率：

Write unit tests for this function, including edge cases and failure paths.
Generate a property-based test for this sorting utility.
Extend this test file to cover missing scenarios around null inputs and invalid states.

用例 5：提升开发速度

Codex 通过加速开发周期的开端与结尾，帮助团队跑得更快。在启动一个新功能时，工程师用脚手架（scaffold）生成样板代码——生成文件夹、模块与 API 桩，无需手动连接每一块就能快速得到可运行代码。

当项目接近发布时，Codex 通过处理那些更小但必不可少的任务——如分诊 bug、填补"最后一英里"的实现缺口、生成发布脚本、遥测钩子或配置文件——来帮助满足紧迫期限。

它也被用于将产品反馈转化为起步代码。工程师常常贴入一个用户请求或规格，让 Codex 生成一份粗略草稿，之后可以回来打磨。

团队轶事
  • "我一整天都在开会，但还是合入了 4 个 PR，因为 Codex 在后台工作。"——ChatGPT Enterprise，产品工程师
  • "Codex 完美地交付了 3-4 个本会在待办列表里搁置的低优先级修复，这让人很有掌控感。"——内部工具，全栈工程师

用以下示例 prompt 试试把 Codex 用于提升开发速度：

Scaffold a new API route for POST /events with basic validation and logging.
Generate a telemetry hook for tracking success/failure of the new onboarding flow, using this template [insert example of your telemetry code].
Create a stub implementation based on this spec: [insert spec or product feedback].

用例 6：保持心流（Staying in flow）

当工程师的日程被切碎、充满打断时，Codex 帮助他们保持生产力。它被用于捕获未完成的工、把笔记变成可运行的原型，或派生出可以稍后 revisiti 的探索性任务。这让暂停与恢复工作变得更容易，而不丢失上下文——尤其是当他们值班或会议很多时。

团队轶事
  • "如果我看到一个顺手就能修的问题，我会派一个 Codex 任务，而不是切换分支，等有空时再 review 它的 PR。"——ChatGPT API，后端工程师
  • "我习惯把 Slack 线程、Datadog 追踪、issue 等转发给 Codex，这样我能专注于高优先级工作。"——基础设施可观测性，API 工程师

用以下示例 prompt 试试把 Codex 用于保持心流：

Generate a plan to refactor this service and split it into smaller modules.
Stub out the retry logic and add a TODO — I'll fill in the backoff logic later.
Summarize this file so I can pick up where I left off tomorrow.

用例 7：探索与构思

Codex 在开放式工作中也很有用，例如寻找替代方案或验证设计决策。你可以提示它用不同方式解决一个问题、探索不熟悉的模式，或压力测试（pressure-test）假设。这有助于暴露权衡、扩展设计选项，并打磨实现选择。

它也被用于识别相关 bug。给定一个已知问题或被弃用的方法，Codex 能识别代码库中其他地方的相似模式，让捕获回归或完成清理工作变得更容易。

团队轶事
  • "Codex 帮我解决冷启动问题——我贴入一份规格与文档，它就脚手架出代码，或告诉我漏了什么。"——ChatGPT Desktop，产品工程师
  • "修完 bug 后，我问 Codex 相似的 bug 还可能藏在哪里，然后派生后续任务。"——检索系统，性能工程师

用以下示例 prompt 试试把 Codex 用于探索与构思：

How would this work if the system were event-driven instead of request/response?
Find all modules that manually build SQL strings instead of using our query builder.
Rewrite this in a more functional style, avoid mutation and side effects.

最佳实践

当 Codex 被给予结构、上下文和迭代空间时，它表现最好。以下是 OpenAI 团队在日常工作中培养的、用以稳定获得价值的一些习惯：

  • 从 Ask 模式开始：对于大型改动，先用 Ask 模式提示 Codex 给出一个实现计划，该计划随后在你切换到 Code 模式时成为后续 prompt 的输入。这一两步流程让 Codex 保持"接地"（grounded），并有助于避免其输出中的错误。Codex 在"范围明确、约需你或队友一小时完成、或几百行代码实现"的任务上表现最好。随着模型改进，预计它能承担的任务规模会增大。
  • 迭代改进 Codex 的开发环境：设置一个启动脚本、环境变量与互联网访问，能显著降低 Codex 的错误率。在运行任务时，留意那些可以在 Codex 的环境配置中纠正的构建错误。这可能需要几次迭代，但长期会带来显著的效率提升。
  • 像写 GitHub Issue 一样组织你的 prompt：当 prompt 镜像你会在 PR 或 issue 中描述一次改动的方式时，Codex 的响应更好。这意味着：在相关时包含文件路径、组件名、diff 与文档片段。使用像"用 [模块 X] 中相同的方式实现它"这样的模式来提示，能改善结果。
  • 把 Codex 任务队列当作轻量待办列表：派发任务来捕获边缘想法、部分工作，或顺手的修复。没有一次就生成完整 PR 的压力。Codex 很适合作为一个暂存区，你可以在重新聚焦时回来处理。
  • 用 AGENTS.md 提供持久上下文：维护一个 AGENTS.md 文件，帮助 Codex 在你的仓库中跨 prompt 更有效地运作。这些文件通常包含命名规范、业务逻辑、已知的怪癖，或 Codex 无法仅从代码推断出的依赖。在文档中了解更多关于组织你的 AGENTS.md 文件的内容。
  • 利用"Best of N"来改善输出：Best-of-N 特性让你能为单个任务同时生成多个响应，以快速探索多个解决方案并挑选最佳者。对于更复杂的任务，你可以审阅若干次迭代，并组合不同响应的部分，得到更强的结果。

展望未来

Codex 仍处于研究预览阶段，但它已经在我们的构建方式上产生了真实影响——帮助我们跑得更快、写出更好的代码，并承担那些原本永远不会被优先处理的工作。

我们对前方的潜力感到兴奋——随着我们的模型变得更好、Codex 更深地集成到我们的工作流中，我们期待解锁更强大的、用它来开发软件的方式。我们将持续分享这一路上所学到的东西。
