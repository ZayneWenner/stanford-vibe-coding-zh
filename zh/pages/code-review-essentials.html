软件团队的代码审查要点

Blake Smith ｜ 2015 年 2 月 9 日

代码审查（Code Review）是任何协作型软件项目的重要组成部分。大型软件系统通常由不止一个人编写，因此一个高效运转的软件团队需要一套稳健的流程，让团队成员以及代码库本身都朝着正确的方向前进。

代码审查（Code Review）是一款强大的工具，它能够：

  1. 帮助团队成员在系统演进时，同步更新自己对系统的心智模型
  2. 确保变更正确地解决了问题
  3. 开启关于设计优缺点的讨论
  4. 在缺陷进入生产环境之前将其捕获
  5. 保持代码风格与组织的统一性

不妨把这些好处看作一套「需求层次」。

让团队成员步调一致

代码审查（Code Review）最关键的作用，是让团队的每一位成员都朝着正确的方向前进。你无法安全地修改一个你不理解的系统，因此代码审查（Code Review）保证了团队在认知上保持一致。当 Bob 提交了一份关于会计子系统的拉取请求（PR）时，Amy 在审查 Bob 代码的过程中，也同步更新了自己对该系统的心智模型。Amy 有机会就自己不理解的部分提出问题，而 Bob 也能从中获益——他得以澄清自己的设计决策，并把工作内容讲解给另一位同事。一个月后，当 Amy 需要去修改会计子系统时，她对该系统的心智模型已经是最新的，可以直接上手。她花在阅读代码、在脑中拼凑系统全貌上的时间变少了，而有更多时间去思考更高层的抽象与设计。每个人都受益，因为所有人都保持同步。

执行一次高质量的拉取请求（PR）

在你写下任何一行改变系统的代码之前，先问自己以下几个问题：

  • 「我现在做的这件事方向对吗？」 来自客户、团队内部成员以及其他相关方的需求总是彼此竞争。在深入之前，这是个让自己理清优先级的好办法。像迭代（iteration）/冲刺（sprint）计划会议这类流程，同样有助于让这件事不跑偏。
  • 「团队是否已经认同这次变更是正确的？」 如果没有，那么最好先通过邮件，或者当面开启一次设计讨论。当大家在设计上先达成一致，你的变更才更有可能被接受。
  • 「我怎样才能把这个变更拆分成易于审查和理解决的小块？」 小的变更更容易被思考和看懂。当团队能迅速理解你的变更时，良好的讨论才会自然产生。如果你的改动过于庞大，同事的眼神会开始发直，你可能只会收到几条关于代码风格的挑剔意见。
  • 「我打算如何测试这次变更，以消灭缺陷并确保正确性？」 你或许有一个 QA 部门，但作为开发者，交付高质量、可运行的软件依然是你的职责。易于测试的软件通常耦合度更低、被拆分成更小的块、也更容易推理。你需要为所有的变更都准备一份测试计划。

我发现，提前回答好这些问题，长远来看替我省掉了大量的头痛。你最不希望发生的事情，就是花了好几天写出一个变更，却因为它存在根本性的设计缺陷或团队分歧而被驳回；或者因为没人能验证它的正确性，导致变更被卡住。再一次强调，目标是在改变系统的同时，让其他团队成员随时了解你的变更。问自己打算如何把工作拆成适口的小块并逐一测试，会在很多方面带来帮助：

  • 它降低了风险
  • 它让变更更易于推理
  • 它推动你走向更好的设计

你宁愿用手术刀做许多小而精准的切口，也不愿用大砍刀来一道巨大的伤口。在大多数增量式开发的场景下，我偏爱手术刀式的开发，而把大砍刀留到需要删除大段死代码的时候。

提交拉取请求（PR）

好，你已经获得了团队对你变更的认可，并且实现了你原本打算构建的设计。那么，实际发送拉取请求（PR）最有效的方式是什么？你为自己的变更付出了很多努力，希望团队其他成员关注你的拉取请求（PR）并给你快速的反馈。怎样才能做到呢？

还记得我前面说的吗——代码审查（Code Review）最重要的部分，是让团队集体的心智模型保持良好对齐？你的其他队友很可能正在做与你完全不同的事情，也许是在系统另一个完全不同的部分。他们的大脑处于完全不同的上下文之中，因此你必须通过提供他们所需的、有助于完成审查的引导来克服这一点。这意味着要写一份条理清晰的变更描述：说明你做了什么改动、为什么这么做，以及任何其他仅读代码无法获得的相关信息。别让你的队友承担超出必要的脑力负担。

我们来看一些拉取请求（PR）描述的好例子与坏例子：

坏例子：

Title: Fix uninitialized memory bug
Description: 

This is the bug Bob and I talked about earlier. I had
trouble with the compiler but managed to make this work. Let me
know what you guys think.

如果你是这份拉取请求（PR）的开发者，停下来，把自己代入代码审查者的角色想一秒。标题含糊不清，引出的问题比答案还多：内存缺陷在哪里？这次变更有多关键？你之前和 Bob 讨论的到底是什么缺陷？你在编译器上遇到了什么麻烦？描述既没有就问题提供任何有用的背景，也没有对你的改动给出任何有帮助的说明。如果这份拉取请求（PR）很长，审查者将不得不一头扎进代码里，在有机会思考「这个变更如何融入系统连贯的设计」之前，先要做一番费力的脑力体操来获取上下文。

下面是一个改进版例子，有助于澄清这次变更集：

Title: Fix process crash on startup from uninitialized memory [#54633]
Description:

This bug was causing process crashes on boot due to a memory
initialization error in our statistics Counter class. I talked this
over with Bob, and we both agree the crashes are a rare edge case
that don't warrant a hot-fix release. Here's a summary of the
changes:

  - Moved the underlying int variable into the class initializer
    to prevent ununitialized memory in the Counter.
  - Reworked the Counter interface to simplify caller conditional
    logic and prevent further off-by-one counting problems.
  - Added a unit test that exposes the crash

Testing: I've verified the test suite still passes, and verified
manually that the crash doesn't happen locally.

这个拉取请求（PR）描述有几点改进：标题足够具描述性，能给审查者一些简短的上下文，并吸引他们点开邮件了解更多。审查者知道这是一次进程崩溃（这通常是非常糟糕的事情），而且还有一个缺陷报告编号，如果审查者想进一步了解问题细节，可以顺着编号读更多内容。新的描述还勾勒出了问题发生的位置，并帮助说明这次修复的关键程度。其中有一份摘要，列出了拉取请求（PR）中高层的结构性改动，这会让审查者在看代码之前，先在脑中形成对改动的图景。代码审查者不应被他们看到的内容吓一跳。这个例子还列出了所执行的测试，这会让审查者确信这些改动是经过深思、充分测试、可以合并的。让审查者轻松地点下「merge（合并）」按钮，就是为他们的成功铺路。

审查者：给出建设性反馈

审查流程接下来要考虑的一环，是给你的同伴给出建设性的反馈。如果目标是清晰与对齐，给出高质量的建设性反馈能帮助每个人更好地理解系统，并推动写出更好的代码。

避免说这样的话：

  • 「这个设计是坏的。」 为什么坏？怎样才能变好？这类陈述会伤害信心，也会挫伤自尊。
  • 「我不喜欢这个改动。」 你为什么不喜欢？你更希望换成什么？不喜欢某样东西没问题，但你应该阐述自己的思路，并就代码可以如何改进给出有用的线索。
  • 「你能把它重写得更清晰一点吗？」 我现在写的到底有什么问题？我该怎样重写？哪里不清晰？这类评论本身就不清晰，也没有给出一条简单的改进路径。

相反，应该说这类话：

  • 「这段代码如何处理负整数？」 这条反馈很具体，能促使开发者自己去把各种结果想清楚。作为审查者，你可能已经知道相关代码在遇到负整数时会崩溃，但更好的做法是让开发者自己领悟到这一点。像这样的问题也可能预示着存在测试缺口，或需要进一步明确范围（scope）。
  • 「这一段让我很困惑，我不理解为什么 A 类要和 B 类对话。」 如果开发者没有提供有帮助的描述，而代码本身又结构凌乱，这类评论有助于推动设计清晰化和代码整洁化。
  • 「看起来你在这里破坏了一个接口边界。那会如何影响用户？」 你指出了自己注意到的一个问题，同时假定对方是故意这么做的，给了他们解释的余地。现在他们可以去推敲破坏接口边界带来的隐性后果，要么为自己的决定给出理由，要么选择去改它。

总体而言，把反馈框定为提问，是追求清晰与正确性的好办法，同时也能帮助开发者在未来改进自己的设计。高质量的创意写作小组通常就是这样彼此反馈的。在创意写作的语境里，说「我不喜欢这个角色」是有害的；而同样的意思可以被框定得更清晰：「在第一章里你的角色温暖而富有同理心，可现在他却冷若冰霜。对我来说他不像一个真实的人。」这就成了可以据此澄清、把问题弄明白的具体反馈。

程序员天生喜欢解决问题、喜欢指出毛病，因此从本性上说，他们喜欢在自己的同伴代码里找问题，以此证明自己有多聪明。别这么做。代码审查（Code Review）是一种让更多人盯住一次变更、揪出关键问题的手段，但你的目标应当是：在解决手头问题的同时，以鼓励团队成员提升技能的方式进行审查。

风格细节

大括号的位置、变量/函数命名、缩进与空格问题都应当被处理，但它们并不是好的代码审查（Code Review）的核心目的（注意我把它们放在了代码审查金字塔的最顶端）。如果你发现团队把 90% 的时间花在挑剔缩进和变量名上，那你们很可能是在把大家的时间浪费在本可以大多自动化的事情上。写一份风格指南，在签入（check-in）时强制规范缩进与空格问题，把时间花在更高价值的问题上。我并不想贬低一致风格的重要性。恰恰相反，拥有一套一致且符合语言习惯的风格，是让你的代码库易于阅读和理解的最简单途径之一。尽管如此，如果你把全部代码审查（Code Review）都聚焦在这些简单任务上，那就该问问自己：你是不是在回避那些更困难、也更重要的工作——让团队在认知上保持对齐，并思考更高层的设计。
