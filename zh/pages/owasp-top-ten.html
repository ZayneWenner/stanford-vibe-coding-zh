OWASP 十大 Web 应用安全风险

当前已发布的最新版本是 OWASP 十大 2025。

旧版本可在 OWASP 十大 2021 和 OWASP 十大 2017（PDF） 获取。更早期的版本可在 GitHub 仓库 中找到。

OWASP 十大（OWASP Top Ten）是面向开发人员和 Web 应用安全的标志性认知文档。它代表了关于 Web 应用最关键安全风险的广泛共识。

被全球开发人员公认为迈向更安全编码的第一步。

企业应当采纳本文档，并启动相应流程，确保其 Web 应用将这些风险降至最低。采用 OWASP 十大，或许是改变组织内部软件开发文化、使其生产出更安全代码的最有效第一步。

OWASP 十大 2025 数据分析计划

目标

收集迄今为止与已识别应用漏洞相关的最全面数据集，以便为十大（Top 10）及其他未来研究提供支持。这些数据应来自多种来源：安全厂商与咨询机构、漏洞赏金计划，以及公司/组织的贡献。数据将被规范化，以便对“人工辅助工具（Human assisted Tooling）”与“工具辅助人工（Tooling assisted Humans）”之间进行水平比较。

分析基础设施

计划利用 OWASP Azure 云基础设施来收集、分析和存储所贡献的数据。

贡献

我们计划同时支持已知身份与伪匿名两种贡献方式。我们更希望贡献者为已知身份；这极大有助于对所提交数据的验证、质量与可信度。如果提交者希望其数据被匿名存储，甚至进一步以匿名方式提交数据，那么该数据将被归类为“未验证（unverified）”而非“已验证（verified）”。

已验证数据贡献

场景 1：提交者身份已知，并同意被标识为贡献方。
场景 2：提交者身份已知，但不愿被公开标识。
场景 3：提交者身份已知，但不希望被记录到数据集中。

未验证数据贡献

场景 4：提交者匿名。（是否应支持？）

当未验证数据成为被分析数据集的一部分时，分析过程将对其加以谨慎区分。

贡献流程

数据可以通过以下几种方式贡献：

  1. 将包含数据集的 CSV/Excel 文件通过邮件发送至 [email protected]
  2. 将 CSV/Excel 文件上传至 https://bit.ly/OWASPTop10Data

模板示例可在 GitHub 上找到：https://github.com/OWASP/Top10/tree/master/2025/Data

贡献周期

我们计划接受针对新十大（Top 10）的数据贡献，截止日期为 2025 年 7 月 31 日，数据时间范围为 2021 年至 2024 年。

数据结构

以下数据元素为必填或选填。
提供的信息越充分，我们的分析就越准确。
在最起码的情况下，我们需要时间周期、数据集中经过测试的应用总数，以及 CWE 列表及包含该 CWE 的应用数量。
如果可能，请提供额外的元数据，因为这将极大地帮助我们深入了解测试与漏洞的现状。

元数据

  • 贡献者名称（组织或匿名）
  • 贡献者联系邮箱
  • 时间周期（2024、2023、2022、2021）
  • 经过测试的应用数量
  • 测试类型（TaH、HaT、Tools）
  • 主要语言（代码）
  • 地理区域（全球、北美、欧盟、亚洲、其他）
  • 主要行业（多种、金融、工业、软件、??）
  • 数据是否包含重复测试或同一应用的多次出现（T/F）

CWE 数据

  • CWE 列表，及已发现包含该 CWE 的应用数量

如果可能，请提供数据中的核心 CWE，而非 CWE 类别。
这将有助于分析，本分析中进行的任何规范化/聚合都将被详细记录。

说明：

如果一位贡献者拥有两类数据集——一类来自 HaT，一类来自 TaH 来源——则建议将它们作为两个独立的数据集分别提交。
HaT = 人工辅助工具（Human assisted Tools，高体量/高频，主要来自工具化）
TaH = 工具辅助人工（Tool assisted Human，低体量/低频，主要来自人工测试）

调查

与十大 2021 类似，我们计划开展一项调查，以识别社区认为重要、但可能尚未在数据中体现出来的最多两个十大类别。我们计划在 2025 年初开展调查，并将以与上次类似的方式使用 Google 表单。调查中的 CWE 将来自当前的热点发现、数据中排在十大之外的 CWE，以及其他潜在来源。

流程

在较高层面上，我们计划执行一定程度的数据规范化；不过，我们将保留一份所贡献原始数据的版本，以备未来分析之用。我们将分析各数据集的 CWE 分布，并可能将部分 CWE 重新归类，以将其合并为更大的分桶。我们将详细记录所采取的所有规范化操作，以便清楚地说明做了什么。

我们计划沿用 2021 年延续的模型来计算可能性（likelihood），以确定发生率（incidence rate），而非频率（frequency），从而评估某个给定应用可能包含至少一个 CWE 实例的概率。这意味着我们关注的不是应用中发现的频率（发现数量），而是包含了一个或多个 CWE 实例的应用数量。我们可以根据数据集中经过测试的应用总数，与每个 CWE 被发现存在于其中的应用数量，来计算发生率。

此外，我们将为排名前 20-30 的 CWE 开发基础 CWSS 评分，并将潜在影响纳入十大的权重之中。

同时，我们也希望探索从所贡献数据集中可以获得的额外洞察，看看还能了解到哪些对安全与开发社区有用的内容。
