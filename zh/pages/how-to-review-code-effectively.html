如何有效地审查代码：一位 GitHub Staff 工程师的理念

GitHub 的 Staff 工程师 Sarah Vessels 分享了她的代码审查理念、区分优秀与糟糕代码审查的标准、她查找与审查代码的策略，以及如何从他人对自己代码的审查中获得最大收益。

作为 GitHub 的一名 Staff 工程师，代码审查是我日常工作的主要关注点之一。过去八年里，我审查了超过 7000 个拉取请求（PR）。为什么这么多？因为代码审查对于构建优秀的软件至关重要，而多一双眼睛往往能发现你原本会遗漏的问题。

我把代码审查视为自己工作中最重要的方面之一。事实上，每当我看到队友有一个拉取请求准备好接受代码审查时，我宁愿放下自己正在处理的任何分支，先去审查他们提议的改动。毕竟，他们的拉取请求已经通过了持续集成（CI）的重重考验，并达到了他们自己判断中「完成」的标准，因此它可能比我进行中的工作更接近可上线状态。我更愿意帮他们的代码冲过终点线，而不是再花费未知的时间去完成我自己的代码。

我越早提供反馈——「这里可能是 nil 并导致错误」「这看起来像是一个 n+1 查询」「如果能给这个方法加个方法签名就好了」——这些反馈就能越快被处理，bug 也就能越快被消灭或功能越快上线。

我想分享我进行代码审查的方式，希望我们都能交付更好的代码。

什么是代码审查？

严格来说，代码审查——通过 GitHub 上的拉取请求审查——允许协作者对拉取请求中提议的改动发表评论、表明他们对该改动的批准，或在拉取请求合并前要求进一步修改。

我把拉取请求看作一段对话的开始。我把它理解为作者在说「我认为这比我们今天的实现更好」。代码审查是塑造产品实现方式的绝佳机会。作为代码审查者，我的工作就是与作者来回讨论，通过提问、质疑假设，总体上充当第二双眼睛，来改进他们的代码。

为什么要审查代码？这对你的职业发展有好处

我从其他审查者对我自己代码的视角中学到了很多，而且在多次收到感谢我及时审查代码的正面反馈后，我知道我的代码审查评论同样帮助了队友提升。简而言之，代码审查是有影响力的，而获得晋升需要展现出你的影响力。

代码审查之所以有影响力，是因为它们有助于交流知识、提高交付速度。它们是很好的、可链接的工作成果，同事和经理可以用它们来展示你有多乐于助人、多有见识。它们能凸显良好的沟通技巧，特别是在需要复杂或有争议改动的时候。因此，在代码审查中好好陈述你的观点，不仅能引导产品的未来、帮助避免事故，对你的职业发展也有好处。

微调你的代码审查流程

如何找到需要审查的拉取请求

我常驻在我的 GitHub 通知收件箱。它是我在浏览器中固定标签的少数几个之一，所以随时可用。每当我等待 CI、在任务之间切换、开始一天的工作，或者 generally 有一点空闲时，我喜欢查看我的收件箱。我在那里找到的大部分拉取请求都是我审查的。GitHub 的各团队往往有一个特定的 Slack 频道作为大本营，那是分享「准备好审查」的拉取请求的好地方——这也是我发现拉取请求的另外一个主要途径。

我还通过 GitHub Slack 集成 订阅某个 Slack 频道来接收与我团队相关的新拉取请求，效果不错。为了过滤在 Slack 中显示的拉取请求，我使用一个团队专属的标签，然后在 Slack 中使用类似 /github subscribe your/repo pulls +label:"your-team-label" 的「subscribe」命令。

提示

你可以在查询中重复使用 team-review-requested: 限定符，以获取多个不同代码所有者团队的待审查拉取请求。

我喜欢用类似 is:open archived:false is:pr org:github -is:draft team-review-requested:github/relevant-codeowner-team 的查询来搜索可能需要审查的未完成拉取请求。通过该查询，我找到 GitHub 组织内开放、未归档的拉取请求，它们不在草稿状态，并且有相关的代码所有者团队作为被请求的审查者。我通常会省略 review:required 搜索限定符，因为即使队友已经审查过，我也有兴趣审查某个拉取请求。毕竟，审查代码不仅帮助作者，也帮助我了解影响我所负责代码的最新改动。

使用审查者团队来管理通知

你不希望代码改动通知 ping 到一个如此庞大的团队，以至于团队中每个人都假定审查这个改动不是自己的责任。这可能导致拉取请求要么无人审查而搁置，要么在应该被审查之前就被合并，因为关键审查者在大量通知中错过了它们。这两种情况都会影响产品质量。

如果你能够，我建议精简你所加入的代码所有者团队数量，让你的通知可控。这样，落入你收件箱的拉取请求就不只是噪音，而是你确实觉得应该审查的东西。虽然大而全的代码所有者团队作为兜底选项尚可，但它们不适合作为自动审查请求的默认第一线。保持你的代码仓库中 CODEOWNERS 文件组织良好，并配以定义清晰的代码边界，以限制通知数量，帮助审查者避免通知疲劳。

限制基于团队的通知的另一种方式是创建一个「一线响应者（first responders）」团队，然后使用自动化根据排班添加和移除团队成员。这可以让你团队专注于他们的日常代码库，而按排班的一线响应者会收到你团队服务区域内拉取请求的通知。例如，使用 PagerDuty API，你可以确定某天谁是一线响应者。然后你可以使用 Octokit 库 来添加和移除团队成员。

用自动化跨团队标准化代码审查

仓库级别的配置和自动化，例如使用 CODEOWNERS 文件 和分支保护规则，有助于跨团队强制执行审查流程标准。其他标准，例如拉取请求中哪些内容值得评论，必须由我们人类来维护。记录你的团队内部代码审查的运作方式，确保任何提供代码审查或提交拉取请求的人都知道如何让他们的拉取请求得到审查、预期的审查周转时间，以及使用了哪些自动化来辅助审查。

一些团队使用项目看板来跟踪有哪些拉取请求进来需要审查；我见过这对一个管理共享 API 的团队很有效，那个领域常被团队之外的人修改。其他团队仅依赖 GitHub 通知，我在代码所有权范围严格、且团队对于随到随审有纪律时，也见过这种方式运作良好。

如果你遵循的是某个特定团队独有的流程，自动化可以帮助向团队之外的人传达期望。例如，如果许多其他团队依赖你团队的审查，你可以用机器人自动在任何请求你团队审查的拉取请求上留言，告诉作者他们可以预期什么时候收到你的回复。

是什么让代码审查变好或变糟？

优秀的代码审查能增加清晰度，并推动代码走向比起点更好的状态。

作为审查者，沟通的清晰度是关键。你要清楚地区分哪些评论是个人偏好，哪些是通过批准前的阻塞项。提供一个你所建议方法的示例，能提升你的代码审查质量，并让你的意思更加清楚。如果你能提供与拉取请求同一代码仓库中的示例，那就更好了——它通过鼓励一致的实现方式，进一步支持你的建议。

相比之下，糟糕的代码审查缺乏清晰度。例如，没有任何评论的笼统批准或拒绝，会让拉取请求作者怀疑审查是否彻底。即使只是在你批准时重申一下你对拉取请求作者意图的理解，也能暴露出你和作者是否达成了相同的理解。

如果一个代码审查没有说清它的建议应当在何时实现，对作者来说也可能是一段糟糕的体验。指出已有的、未改动的代码应当被重构，或者应当处理一个额外的情况，这都没问题，但重要的是要说明这些是否是通过批准的前提条件。如果拉取请求在没有你的建议的情况下也可以合入，一定要说明这一点。把小的 diff 保留下来、作为单独的拉取请求分开上线，可能更安全。

下面是一个展现了针对性、并清楚传达所建议实现的代码审查评论：

「我看到你的新方法匹配了这个文件中已有的风格，接收了 [X] 个参数。参数这么多会损害可读性，也意味着这个函数做的事太多。你觉得在后面的一个拉取请求中重构这个方法以及已有的那些方法，以减少它们接收的参数数量，怎么样？」

这条评论做得好的地方：

  • 提供了具体细节。
  • 引用了具体的代码或问题。
  • 提出了问题的解决方案。
  • 引用了证据或提供了解释

在另一个极端，以下是一些本可以写得更好的审查评论示例：

「我不喜欢这个。」 —— 审查者不喜欢什么？他们心里有没有一个可以明确说出的替代方案？

可能的改进：

  • 「这一行做了很多事，我们能不能简化它以提升可读性？」
  • 「我认为这会因为有 n+1 查询而出现性能问题。」
  • 「我们能不能改用 [首选框架] 的方案，而不是自己写一套自定义实现？」

「这行不通。」 —— 为什么这些改动行不通？

可能的改进：

  • 「这行不通，因为 [X]，参见这个相关问题：[issue 链接]。」
  • 「之前在 [拉取请求链接] 中试过，因为 [X] 而没有成功。」
  • 「如果你在 [X] 上遇到问题，可以试试 [替代方案]。」

「我认为这修复了一个 bug。」 —— 我很喜欢这个提醒，但有没有额外的上下文（比如 issue 链接）能让它更清楚？

可能的改进：

  • 「我认为这修复了 [issue 链接]。」
  • 「这是在修复 [issue 链接] 里的 bug 吗？」
  • 「这看起来像是我们在 [失败构建链接] 中遇到的 bug。谢谢修复！」

如何给出好的代码审查

提问

我把拉取请求作者看作对其拉取请求所做改动拥有最多上下文的人。我可以基于我的历史——我在 Ruby on Rails 单体仓库、TypeScript 或某个高流量数据库方面的工作经验——指出我看到的问题，但我信任作者对我问题的回答。我把他们对具体细节的理解看得比我的更好。

提示

如果你刚接触某个代码库或团队，在代码审查中提问，可以了解技术栈以及有哪些内部工具和库可用。你审查的每一个拉取请求，都是一次了解作者为什么偏好某一种而非另一种方法的机会。

我也很喜欢问一些涉及代码中假设的问题。他们处理的数据是什么形态？是否存在不匹配该形态的数据？代码对此响应得好吗？代码是否消耗大量资源？它会表现良好吗？作为审查者，我最喜欢的回应是作者提供一个自动化测试来验证这些场景下的行为。我第二喜欢的回应是经验数据，例如来自我们数据仓库的一个查询，或一张显示为什么这些场景不是问题的 Datadog 图表。

作为拉取请求作者，我很乐意收到问题。当有人提问时，这为我留出空间来解释为什么我对自己的改动有信心，并在必要时引用 issue、查询或图表。这也让我能与他人分享我的知识和经验。作者不仅看到我的回应，其他审查者以及未来可能追查某个历史决策上下文的读者也能看到。

给予肯定

除了提问，对拉取请求中你认同的部分发表评论也是好的做法。这些评论可以突出表明你阅读并理解了所改动的内容，或者你验证了代码中的某个假设。以下是一些示例：

  • 「看起来这与本模块中其他类使用的模式一致。」
  • 「谢谢为这个加了测试！」
  • 「这比之前可读性强多了。」

根据我的经验，处于这类评论的接收端也让人感觉很好。收到代码审查有时会让人精疲力竭。当我在应对多方的问题和建议时，收到几条不向我索取任何东西、反而支持和认可我已投入工作的评论，会是很好的鼓舞。

注意偏见与假设

很容易让你对审查者或其改动所在代码区域的偏见，影响你的审查。你习惯了某人在某个领域工作，或具有某种程度的资历，就假定他们知道自己在做什么——但每个人都会犯错。你的眼睛审视他们的改动、你用问题检验他们的假设或验证你自己的假设，能在问题被部署之前就抓住它。

我非常推崇写测试，因为它们能消除一些偏见。当你写一个测试来检查代码是否正常工作，你不必只听作者的一面之词，你只需看测试是否通过——当然，前提是你把测试写对了。😅

我也非常鼓励初级开发者在代码审查中向资深开发者提问，即使他们认为自己的问题很傻或答案显而易见。如果对你来说不明显，那就是合理的。对别人来说也不会明显！提出问题，给作者留出写下答案的空间，并为后来者保留这一点教育意义。

批准还是不批准

我把我的审查看作一道可能阻止他人改进我们产品的阻塞关卡，所以我审慎地 withholding 批准。我常常有个人偏好，并会建议我希望作者做的可选改动，但我不会仅凭这些就 withholding 批准。如果我对某人的拉取请求有建议，但只要它保持现状就不会搞垮生产环境、不会对用户产生负面影响，或不会以其他方式造成问题，我就会带着这些评论予以批准。作者可以选择在合并拉取请求之前处理我的反馈，也可以在另一个分支中跟进。

提示

使用 特性开关（feature flags） 并让你的拉取请求保持小巧。你的改动越不可怕，它在生产环境中被回滚的速度就越快，我也越容易批准它！

在审查代码时，要记住你的建议的重要性。为了落实你的建议而推迟上线是否值得？让作者经历看到你的反馈、做出建议的改动、等待 CI、再次审查、部署、最终合并的完整周期，是否值得？如果缺少某条建议并不会让某人的一天变得更糟，那就让作者自己决定要不要、以及何时做这个建议的改动。

「Request changes」选项会阻止拉取请求被合并，直到审查者回来并批准它。我很少使用它，因为它通常感觉过于生硬。我信任我的团队知道何时批准一个拉取请求，所以队友的批准可以替代我的。同样，我信任拉取请求作者会尊重我的反馈并加以考虑，而不是仅仅因为别人批准了、而我没批准就盲目合并。我几乎唯一会选择「Request changes」选项的时候，是当我认为是 immediate 安全问题、并担心他们在合并前看不到我的顾虑。

使用 AI 编程工具时，代码审查为何仍然重要

AI 编程工具通常包含各种防止错误或不安全代码的防护机制，但不要被虚假的安全感麻痹。作为掌舵的人类审查者，你是最后一道防线，应当以同等程度的勤勉审查所有代码。

如何从代码审查中获得最大收益

审查你自己的代码

GitHub 资深软件工程师 Paul Smith 教会我在请他人审查之前先审查自己的拉取请求，我也建议你这样做。先做一遍，对非显而易见的改动、或那些如果你在别人拉取请求中看到也会提问的改动，留下行内评论。自我审查也有助于判断一个拉取请求是否过大、是否应该拆分而受益。

特别推荐：如果你在意保持拉取请求小巧，可以利用 lerebear/sizeup-action 自动给拉取请求打上标明其复杂度和大小的标签。

欢迎合并后的审查

如果我碰巧在有人有机会审查之前就合并了一个拉取请求，我仍然欢迎他们的审查。如果我的拉取请求造成了破坏或有非预期后果，在拉取请求上如实评论，会留下一条线索，帮助未来的读者追查发生了什么！

如果我收到一个已合并拉取请求的审查，我会像它在合并前那样处理反馈。也许会是一条解释我视角的评论，也许是额外的拉取请求来迭代我最初交付的代码。也许会开新的 issue 来记录需要做的额外工作。

使用草稿拉取请求

当你创建一个新的拉取请求时，可以选择将其设为草稿。我非常依赖草稿阶段 来表明我是否想要审查。例如，如果必需的 CI 构建失败，或者我还没做完，我会把它保持在草稿状态。我也倾向于对别人的拉取请求有同样的预期：如果是草稿，我假定作者还没准备好接受审查。如果标记为「准备好审查」，我假定获得足够批准就是阻止他们部署拉取请求的唯一因素。

草稿状态意味着拉取请求尚未完成，所以我在解决合并冲突或处理审查者反馈时，会把拉取请求移回草稿。如果我必须修改代码，我会先把它标记为草稿，以免让已经审查过的人不堪重负。当我把它移回「准备好」状态时，会向那些审查者发送一条 GitHub 通知，让他们可以再看一眼。

保持大度

有句话叫「你用蜂蜜比用醋能抓到更多苍蝇」。我希望我的拉取请求上有审查，所以我喜欢回复拉取请求上的评论——尤其是当我不同意审查者时。即使我不写回复，我也常常用 👍 表示同意，或用 ❤ 表示感谢。

我想让审查者相信他们的建议不会被遗忘，所以我通过评论让他们保持知情。如果我同意他们的建议——比如进一步重构已有代码——我可能会直说，同时也会对在当前拉取请求中做这个改动提出保留意见。当我在后面的拉取请求中处理他们的反馈时，我会回来提供链接，让审查者知道他们的反馈没有被置若罔闻。

我还会在实现了建议改动的后续拉取请求中 @ 提及他们，并附上一条说明：「这处理了 @某某 在 <前一个拉取请求 URL> 中的反馈。」这既为其他读者提供了上下文，也是对原始审查者的致意，给予他们应得的认可。

当你兑现承诺、在后续分支中处理反馈时，有助于与审查者建立信任，这能让他们更放心地批准你未来的拉取请求，因为他们知道你不会把事情留半成品。

总结

代码审查对产品质量的重要性怎么强调都不为过，尤其是在 AI 代码生成时代。在我的职业生涯中，很多时候仅仅因为多了那双眼睛，就抓到了一个 bug，或避免了一起事故。代码审查非常值得投入时间，无论是花在日常审查中、在打磨流程上，还是在构建自动化来支持它。开发者现在彻底审查拉取请求，比日后处理一个已经上线的问题要更快、更少痛苦。

感谢你足够在意代码质量，读到了我关于代码审查的理念。你最近检查过你的审查队列吗？也许现在是把这些想法付诸行动的好时机。

如果你想进一步了解如何在 GitHub 上使用拉取请求审查，可以查看 GitHub Community 上由 Staff DevOps Architect Mickey Gousset 和 Staff DevOps Architect Joshua Johanning 发布的讨论审查拉取请求的 5 个技巧。
