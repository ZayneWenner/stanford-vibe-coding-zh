模型上下文协议（MCP）：面向开发者的全面介绍

认证与身份

2025 年 3 月 28 日

作者：Reed McGinley-Stempel

摘要

模型上下文协议（MCP） 是一个开放标准，用于在大语言模型（LLM）与外部数据及服务之间架起桥梁，让大语言模型能够以一致、安全的方式进行结构化的 API 调用。本文将为开发者介绍 MCP，解释它为何对连接 AI 系统有价值，将其与 ChatGPT 插件、手动 API 集成等现有方案进行比较，并深入探讨它近期对基于 OAuth 的认证的支持。我们还会看一些代码，实地感受 MCP 的运行。

MCP 充当 AI 工具与外部服务之间的通用适配器，免去为每个工具或 API 编写定制集成代码的需要。正如 USB-C 简化了各类设备之间的连接，MCP 为 AI 模型调用外部函数、检索数据或使用预定义提示提供了一种统一的方法。其核心在于，MCP 提供了一套接口，可以连接到许多不同的系统。

什么是模型上下文协议（MCP）？

MCP 本质上是 AI 应用与外部工具或数据源之间的通用适配器。它定义了一套通用协议（基于 JSON-RPC 2.0），让 AI 助手能够以结构化的方式调用函数、从外部服务获取数据，或使用预定义的提示。不再需要每个大语言模型应用都为每个 API 或数据库编写定制代码，MCP 为所有交互提供了一门标准化的「语言」。

MCP 层让 AI 应用能够安全地访问外部数据源和工具并与之交互。它充当大语言模型（LLM）与各种数据库、应用或 API 之间的桥梁，促进无缝集成与功能实现，而无需大量定制编码。

MCP 使用客户端-服务器架构来实现这一点。由 AI 驱动的应用（例如聊天机器人、IDE 助手或智能体）充当宿主（host） 并运行一个 MCP 客户端（client） 组件，而每个外部集成则作为一个 MCP 服务器（server） 运行。服务器通过 MCP 协议暴露能力（如函数、数据资源或提示模板），客户端连接到它以使用这些能力。这种分离意味着 AI 模型不直接与 API 对话，而是经由 MCP 客户端/服务器的握手来结构化交换。

来源

MCP 为何有价值

在传统架构中，将 AI 模型连接到外部数据或操作是繁琐且临时的。开发者往往必须为模型要使用的每个 API 或数据库编写一次性集成，为每个集成处理不同的认证、数据格式和错误处理。MCP 通过标准化这些交互改变了局面。主要好处包括：

  • 快速的工具集成：借助 MCP，你可以插入新能力，而无需为每个都从零定制编码。如果存在一个面向 Google Drive 或某个 SQL 数据库的 MCP 服务器，任何兼容 MCP 的 AI 应用都能连接到它并立即获得该能力。这对自动化来说是巨大的胜利——AI 智能体可以按需要获取文档、查询数据库或调用 API，只需添加相应的服务器即可。这就像拥有一座现成的「插件」库，它们都说同一种语言。MCP 服务器是轻量级程序，通过标准化协议暴露特定能力，充当 Cursor 与各种外部工具或数据源之间的中介。
  • 自主智能体：MCP 赋能更具自主性的 AI 行为。智能体不再局限于其内置知识，它们可以在多步工作流中主动检索信息或执行操作。例如，一个复杂的智能体可能使用 MCP 从 CRM 收集数据，然后通过通信工具发送邮件，再在数据库中记录一条信息——全部在一个无缝的链条中完成。通过促成流畅的、上下文感知的多步交互，MCP 帮助 AI 智能体更接近真正的自主任务执行。正如一位观察者所指出的，MCP 通过给予 AI 标准化的真实世界工具与数据访问能力，把一个孤立的「大脑」变成了多才多艺的「执行者」。
  • 降低摩擦与搭建成本：由于 MCP 充当通用接口，开发者不必再为维护各自独立的集成而碎片化精力。一旦某个应用支持 MCP，它就可以通过单一机制连接到任意数量的服务。这极大地减少了每次想让 AI 使用新 API 时所需的手动搭建。团队可以专注于更高层的逻辑，而不必第十次重写连接代码。正如 Anthropic 所说，MCP 用更简单、更可靠的单一数据访问协议，取代了碎片化的集成。
  • 一致性与互操作性：MCP 跨工具强制执行一致的请求/响应格式。这意味着你的 AI 应用不必分别处理服务 A 的某一种 HTTP 响应、服务 B 的另一种 XML，等等。模型的输出（函数调用）和工具的结果都以统一的 JSON 结构传递。这种一致性让调试和扩展都更容易。它还让你的集成逻辑具备面向未来的能力——即使你更换底层的模型供应商，MCP 面向工具的接口依然不变。
  • 双向上下文：与简单的 API 调用不同，MCP 支持在模型与工具之间维持上下文和持续的对话。除了工具之外，MCP 服务器还可以提供提示模板（Prompts）（针对某些任务的预定义提示模板）和资源（Resources）（如文档之类的数据上下文）。这意味着 AI 不仅能「调用一个 API」，还能摄取参考数据，或遵循由服务器引导的复杂工作流。该协议被设计为支持丰富的交互，而不仅仅是一次性查询。这在编程助手（AI 可能通过 MCP 与开发环境迭代）或需要与各种数据源来回沟通才能完成的复杂决策任务中尤为有用。

简而言之，MCP 为增强大语言模型带来了可扩展、即插即用的方式。它让 AI 系统能够安全地获取它们所需的「实时」数据与操作，而无需每位开发者都重新发明轮子。MCP 的早期采用者已经为 Google Drive、Slack、GitHub、数据库等工具构建了服务器——展示了 AI 智能体如何使用 MCP 与企业内容仓库、DevOps 工具及其他真实世界系统协作。


MCP 架构 —— 工作原理一览

客户端-服务器结构

MCP 遵循清晰的客户端-服务器架构：

  • MCP 客户端（MCP Client）：内嵌于 AI 应用（聊天机器人、IDE 助手、自动化智能体）中。
  • MCP 服务器（MCP Server）：暴露外部能力，如函数（工具）、资源（数据）和提示（模板）。

所有交互都通过标准化的 JSON-RPC 消息进行，维持安全、结构化的交换：

JSON-RPC 请求示例：

例如，为了列出可用工具，MCP 客户端会发送如下请求：

{
  "jsonrpc": "2.0",
  "id": 1,
  "method": "tools/list",
  "params": {}
}

服务器会用一个结构化的 JSON 回复，列出工具（每个工具带有名称、描述和输入模式）。例如，一个服务器可能会声明一个 get_weather 工具，并描述它需要的输入。

{
  "jsonrpc": "2.0",
  "id": 1,
  "result": [
    { "name": "get_weather", "description": "Retrieves weather data.", "schema": { "location": "string" } }
  ]
}

之后，当大语言模型决定使用某个工具时，客户端会发起相应的调用。MCP 服务器执行该函数，并在结构化的 JSON 响应中返回结果。MCP 客户端（在宿主应用内部）随后可以将该结果反馈回模型的上下文或回复中。在实践中，宿主应用居中协调这一过程：它将大语言模型的意图（通常通过模型的函数调用输出）转化为一个 MCP 请求，再把服务器结构化的结果传回大语言模型。这种双向交换是安全且受控的——模型只能调用服务器暴露的特定工具，所有进出数据都经由定义的协议传输。

构建与部署 MCP 服务器

构建与部署 MCP 服务器，是在 AI 集成中利用模型上下文协议（MCP）的关键一步。MCP 服务器充当 AI 模型与外部数据源或工具之间的中介，实现无缝的通信与数据交换。MCP 的一个突出特性是它在服务器开发上的灵活性。开发者可以使用任何能够向 stdout 输出或提供 HTTP 端点的编程语言，从而自由选择自己偏好的语言和技术栈。

在构建 MCP 服务器时，架构与设计至关重要。MCP 遵循客户端-服务器架构，一个宿主应用可以连接到多个服务器。这种架构带来了可扩展性与灵活性，让开发者能够设计出处理各种任务和功能的 MCP 服务器，例如数据处理、工具集成或 AI 模型管理。

部署 MCP 服务器可以在多种环境中进行，包括本地开发环境、云平台或本地基础设施。例如，Cloudflare 提供了一个稳健的平台来构建和部署远程 MCP 服务器，使 MCP 部署的管理与扩展更加容易。这种灵活性确保 MCP 服务器能够适配不同应用和环境的特定需求，无论是用于开发的本地设置，还是用于生产环境的云方案。

通过关注设计良好的架构并利用 MCP 的灵活性，开发者可以创建强大且可扩展的 MCP 服务器，增强 AI 模型的能力，使它们能够与外部数据源和工具无缝交互。

MCP 客户端与工具

MCP 客户端与工具是模型上下文协议生态系统中必不可少的组成部分。MCP 客户端是连接到 MCP 服务器以访问外部数据源或工具的应用。这些客户端可以使用各种编程语言和框架构建，如 Python、JavaScript 或 Java，为开发者提供选择最适合其需求的工具的灵活性。

另一方面，MCP 工具是为 MCP 客户端提供特定能力或功能的软件组件。这些工具可以与 MCP 服务器集成，以实现数据处理、AI 模型管理或工具集成等特性。MCP 工具的例子包括 Claude Desktop（提供与 AI 模型交互的聊天界面）和 Cursor（提供用于扩展 AI 能力的插件系统）。

开发者可以构建自定义的 MCP 客户端与工具，以满足特定的用例或需求。这种灵活性促进了 MCP 生态中的创新与实验，使开发者能够创造出崭新而令人兴奋的应用。无论是用于数据分析的专用工具，还是与多个 MCP 服务器集成的客户端应用，可能性都极为广阔。

通过利用 MCP 客户端与工具，开发者可以创建稳健而多用途的应用，充分释放 AI 模型的潜力，使它们能够与广泛的外部数据源和工具无缝交互。

⚠️ 依赖框架

我们来比较几种在 MCP 之前或与之并存的方案：

  • 定制集成与 API 密钥管理：最常见的传统做法是，为每个服务编写定制代码，并向大语言模型提供凭据（API 密钥或 token）来使用这些集成。例如，你可能写一个 Python 函数来查询某个 API，赋予大语言模型调用该函数的能力，并在后端手动处理 API 密钥。这种方式劳动密集且难以扩展——每新增一个数据源都需要新代码，每个环境都必须安全管理 API 密钥。它常常导致脆弱的系统，因为每个集成都是独一无二的。相比之下，MCP 将这些交互集中并标准化：AI 智能体只需处理 MCP 协议，任何 MCP 服务器（面向任何服务）都能即插即用地工作。新增服务器完全无需改动客户端代码。此外，MCP 为认证（后文讨论）提供了正式的结构，因此向 AI 交出 API 密钥不再是临时行为，而是通过安全协议进行。
  • ChatGPT 插件（OpenAI 插件）：2023 年，OpenAI 为 ChatGPT 引入了插件系统，允许模型调用由 OpenAPI 规范定义的外部 API。这是迈向标准化工具使用早期的一步，但它有局限。每个插件本质上都是它自己的一小套集成（带有自己的 API 模式和认证），需要单独构建/托管。由于是专有方案，只有某些平台（如 ChatGPT 或 Bing Chat）能使用这些插件。插件也大多是单次调用——模型调用一个 API 获取信息，没有持久连接或持续交换。MCP 的不同之处在于它是开放且通用的（不绑定于某一家供应商或接口），并且支持丰富的双向交互与持续上下文。可以把 ChatGPT 插件看作封闭工具箱里的专用工具，而 MCP 是一个任何开发者或 AI 平台都能使用的开放标准工具包。MCP 标准化的认证（尤其是 OAuth）也意味着它能以比 ChatGPT 系统中逐个插件的 OAuth 流程更统一的方式，处理对用户数据的安全访问。总之，ChatGPT 插件展示了为 LLM 标准化 API 访问的价值，但 MCP 更进一步，将其变成了一个开放协议，并实现了 AI 与服务之间的持久「对话」。
  • LLM 工具框架（LangChain、智能体库）：在 MCP 之前，许多开发者使用 LangChain 等框架为模型提供工具。在这种设置中，你定义一组工具函数（带描述）和智能体的提示逻辑，让大语言模型可以决定使用它们。这能工作，但每个工具在幕后仍需要定制实现——LangChain 最终在其库中维护了几百个工具集成。本质上，LangChain 提供了一个面向开发者的标准（一个 Python 类接口）来将工具集成到智能体的代码库中，但没有为模型在运行时动态发现新工具提供任何支持。MCP 与这些框架是互补的，它将标准化转向了面向模型。借助 MCP，一个智能体可以发现并使用任何 MCP 服务器提供的工具，即使智能体的代码事先并未显式包含该工具。事实上，LangChain 已经增加了支持，可以把 MCP 服务器当作又一个工具来源——这意味着用 LangChain 构建的智能体可以轻松调用 MCP 工具，利用不断增长的 MCP 服务器生态。区别在于，MCP 将接口固化在协议之上（JSON-RPC，带元数据等），使其更容易插入不同环境，而不仅限于 Python 框架。类似地，OpenAI 原生的函数调用特性可以看作处理函数调用的格式化（模型输出一个 JSON 函数调用），而 MCP 以标准化的方式处理该调用的执行。OpenAI 的函数调用与 MCP 经常协同工作：大语言模型产生一个结构化的调用，MCP 客户端/服务器执行它并返回结果，二者结合实现了无缝的工具使用。

本质上，MCP 并非第一个尝试将 LLM 与外部 API 连接的方案——但它从那些过往方案（插件、工具库等）中吸取经验，统一了解决方法。它提供了一个开放的、与模型无关的协议，简化了集成与认证。特别是在安全和认证方面，MCP 的设计（支持 OAuth）避免了逐个插件的密钥拼凑、或把原始 API 密钥交给模型的做法。取而代之的是，认证可以作为协议的一部分，以一致、标准化的流程处理——相比现状是一大进步。

MCP 实战：技术深入

让我们一步步走一遍一次典型的 MCP 交互，以巩固对其工作方式的理解，并看一些代码。假设我们有一个 AI 助手，想使用一个提供一组工具（比如某个假想的「Neon」数据库服务）的 MCP 服务器。高层流程是：

1. 连接到 MCP 服务器 —— 宿主应用（AI 助手）初始化一个 MCP 客户端，并与服务器建立连接。根据服务器位置，这可以通过本地进程（stdio）或远程 HTTP 流（SSE）进行。在底层，客户端发送一个 initialize 消息来握手协议版本与能力。

2. 发现可用的工具/资源 —— 客户端随后查询服务器提供什么。如前所示，它可能发送 {"method": "tools/list"} 并取回工具定义列表。助手可以利用这点告知大语言模型（例如，根据实现方式，将工具列表包含在系统提示中，或通过模型的函数模式）。例如，使用某个 SDK，这可能只需一行代码：

const tools = await mcpClient.request({ method: 'tools/list' }, ListToolsResultSchema);

它会返回一个结构化的工具列表。每个工具条目都有名称、描述和输入的 JSON 模式， 这样 AI 就知道它能做什么。

3. 大语言模型选择工具 —— 当用户向 AI 提出需要外部操作的问题时，大语言模型（通常通过提示工程或函数调用能力）确定应当使用某个工具。例如，用户问：「AAPL 股票的最新价格是多少？」 大语言模型看到它应当调用 get_current_stock_price(company="AAPL", format="USD")。宿主应用捕获这一意图（例如，OpenAI 的函数调用 API 会返回函数名和 JSON 格式的参数）。

4. 通过 MCP 调用工具 —— 客户端现在向服务器发送一个 tools/call 请求，带上所选工具名和参数。前面我们看过这个的示例 JSON。在代码中，使用某个 SDK，它可能看起来像：

const result = await mcpClient.request({
    method: 'tools/call',
    params: { name: toolName, arguments: toolArgs }
}, CallToolResultSchema);

这将使服务器在其一侧执行该工具的处理函数。服务器可能在调用某个外部 API、执行数据库查询，或执行该工具封装的任何逻辑。结果（可能是一个简单值，也可能是一个复杂的 JSON 对象）在 MCP 响应的 result 字段中发回。

5. 将结果返回给大语言模型 —— MCP 客户端收到工具的输出。现在宿主应用可以将其整合回 AI 的回复中。在许多智能体设置中，模式是将结果注入对话，并让模型继续。例如，助手随后可能呈现：「AAPL 的当前股价是 $173.22（USD）。」如果使用自动化循环，可以将结果提供给模型（或许作为一条系统消息附加到对话中，如「get_current_stock_price 的结果：…」），模型便可以带着这些信息继续回答用户的查询。

下面是一个简化的示例，展示在使用 Anthropic 的 Claude（原生支持工具使用）时，如何调用工具并在对话中使用其结果：

// 1. 将用户提示连同可用工具的上下文一起发送给 LLM
const response = await anthropicClient.complete({
  prompt: "User: Can you list my projects?\nAssistant: ",
  model: "claude-3.5",
  tools: tools // 来自 MCP 服务器的工具列表
});
for (const msg of response.messages) {
  if (msg.type === 'tool_use') {
    // 2. LLM 决定使用某个工具
    const { name, args } = msg;
    // 3. 通过 MCP 调用该工具
    const toolRes = await mcpClient.request({ method: 'tools/call', params: { name, arguments: args } });
    // 4. 注入工具结果并恢复 LLM
    await anthropicClient.send({ role: 'system', content: `Tool result: ${toolRes.result}` });
  } else {
    // 5. 处理正常的 LLM 回复（工具结果很可能已整合）
    console.log("Assistant:", msg.content);
  }
}

实际上，框架已经为你处理了其中大量工作，但上面的伪代码勾勒了 MCP 如何嵌入循环。关键在于，MCP 提供了标准化的调用/响应层，供 AI 智能体的代码接入。无论你使用的是 OpenAI、Anthropic 还是其他大语言模型，MCP 都保持不变——它是模型意图与外部操作之间的粘合剂。

通过使用 MCP，开发者获得了一条清晰、结构化的管道来扩展 AI 能力。代码变得更易维护（因为你调用的是通用的 mcpClient.request，而非各处针对特定服务的代码），AI 也变得更强大（因为它可以接入任何已连接 MCP 的服务）。调试也更容易——你可以监控 JSON-RPC 消息，精确看到请求了什么、返回了什么，而不必去解析模型生成的文本来寻找线索。

早期局限（无内置认证）

当 MCP 刚出现时（2024 年底），它提供了用于工具与数据交换的核心协议，但缺乏用于连接远程服务器的标准化认证机制。在实践中，早期的 MCP 演示与实现往往要求将 MCP 服务器运行在本地或受信任的环境中，在那里认证不是大问题（因为 AI 与服务器运行在同一台机器上）。例如，开发者可以在自己的 localhost 上运行一个面向 Google Drive 的 MCP 服务器（使用预先获取的 token），然后让 AI 应用指向它。但在互联网上使用 MCP、或与第三方服务一起使用，在没有正式认证流程时就很棘手。

许多最初的 MCP 服务器假定用户会在启动时手动向服务器提供凭据或 API 密钥。例如，Anthropic 的快速上手建议通过配置或命令行提供你自己的凭据（API 密钥、token）来运行预构建的服务器。这意味着服务器本身能访问你的密钥，而 MCP 客户端只是信任该服务器。虽然这在个人或单用户场景下可行，但对于多用户应用或云托管的智能体却难以扩展。当时没有标准握手让 AI 智能体说：「嘿，我被授权代表用户 X 访问此服务；这是我的凭据。」

本质上，早期的 MCP 客户端除了带外方式（如预先共享 token，或不带认证运行）之外，无法向 MCP 服务器认证身份。这是一个显著的局限——MCP 被设计为开放且基于互联网的，但没有认证标准，安全的远程使用就受到了阻碍。

缺乏认证标准意味着MCP 客户端无法安全地自行连接到任意服务器。你要么把客户端 ID/API 密钥硬编码进客户端（在分布式应用中并不理想），要么只能不带认证运行，并假定只有授权用户才能访问到服务器（通常靠把它留在本地）。显然，为了让 MCP 发挥全部潜力（例如以安全方式将 AI 智能体连接到云托管的数据源），需要更好的方案。好消息是社区认识到了这一点，并已将基于 OAuth 的认证纳入 MCP。

OAuth 2.0 认证流程

为了解决最初的认证局限并增强安全连接能力，MCP 采纳了 OAuth 2.0——一个广受认可且稳健的认证标准。OAuth 2.0 提供了一个安全、可扩展的框架，使 MCP 客户端能够安全地与远程服务器、云托管资源和多用户环境交互。将 OAuth 2.0 集成到 MCP 的关键组成部分与好处包括：

  1. 动态客户端注册（DCR）：模型上下文协议支持动态客户端注册，允许客户端向 OAuth 服务器自动注册。这免去了手动客户端配置或硬编码凭据的需要，显著简化了开发者的部署。
  2. 自动端点发现：MCP 利用标准化的元数据 URL（遵循 OAuth 的发现协议）让客户端自动发现 OAuth 端点。这减少了配置开销，使 MCP 部署更容易、更灵活。
  3. 安全的授权与令牌管理：客户端安全地获取精确匹配用户权限和访问范围的 OAuth token。这确保客户端只访问用户明确许可的资源，提升了安全性和合规性，尤其是在多用户和云环境中。
  4. 可扩展且安全的多用户支持：OAuth 2.0 的设计天然支持多个并发用户和服务，解决了 MCP 早期的一大局限。应用现在可以无缝地为大量用户同时处理授权流程，这对广泛的云采用至关重要。

调试与故障排查

调试与故障排查是使用 MCP 服务器和客户端时的关键环节。MCP 提供了各种工具和技术来进行调试与故障排查，确保开发者能高效地识别并解决问题。这一过程中的关键工具之一是 MCP Inspector——一个用于 MCP 服务器的交互式调试工具。

MCP Inspector 让开发者能够测试和检查 MCP 服务器，识别并解决 MCP 服务器集成中的问题。该工具提供了 MCP 客户端与服务器之间交互的详细视图，使定位问题、理解根本原因更容易。此外，MCP 还提供了一份全面的调试指南，列出了常见问题与解决方案，帮助开发者快速排查并解决问题。

在调试 MCP 服务器时，考虑系统的架构与设计至关重要。开发者应当识别导致问题的具体组件或模块，并使用 MCP Inspector 等工具来诊断并解决。通过聚焦系统化的调试方法并利用可用工具，开发者可以确保他们的 MCP 集成稳健可靠。

MCP 的实际应用

模型上下文协议（MCP）在各行业与领域有各种实际应用。MCP 的主要用例之一是在 AI 集成中，它实现了 AI 模型与外部数据源或工具之间的无缝通信与数据交换。

MCP 可用于多种应用，例如：

  • 构建 AI 驱动的聊天机器人：这些聊天机器人可以访问外部数据源或工具，为用户提供准确且最新的信息。
  • 创建 AI 驱动的工作流：MCP 使 AI 模型与外部系统或数据源集成，自动化复杂工作流并提升效率。
  • 开发 AI 模型：这些模型可以与外部工具或数据源交互，增强其能力并给出更准确、更相关的输出。
  • 赋能 AI 驱动的自动化：在金融、医疗或制造等行业，MCP 可以自动化任务与流程，提升生产力并减少错误。

MCP 的灵活性与适应性，使其成为希望在其应用中利用 AI 与机器学习的开发者和组织的理想方案。通过为 AI 模型提供与数据源和工具交互的标准化接口，MCP 促进了 AI 生态中的创新与实验。这种标准化方法不仅简化了集成过程，还确保 AI 模型能访问它们发挥最佳表现所需的数据与工具。

总之，MCP 为 AI 应用打开了一个充满可能性的世界，让开发者能够创建更集成、更自主、更可扩展的方案。无论是用 AI 驱动的聊天机器人增强客户服务，还是在工业环境中自动化复杂工作流，MCP 都提供了将这些创新变为现实所需的工具与框架。

结论

模型上下文协议（MCP）是 AI 开发中令人兴奋的进展，因为它让开发者能够安全、高效地将我们日益智能的语言模型，连接到以往难以连接的广阔软件与数据世界。通过引入一套通用协议，MCP 让我们能够构建更集成、更自主、更易扩展的 AI 系统。我们不再需要为每个新工具编写一次性插件或给模型脆弱的指令，而是拥有了一个连贯的框架，让 AI 智能体可以在适当的监督与安全保障下，即时发现并使用工具。

虽然该协议仍在演进（认证是近期的增补，标准化服务器发现等更多特性也在路上），但很显然，MCP 或类似的东西将在下一代 AI 应用中扮演关键角色。对开发者而言，现在正是熟悉 MCP 概念的好时机。无论你是要用公司专属知识增强聊天机器人，还是构建一个自动化工作流的 AI 智能体，MCP 都能通过处理好工具集成的「管道」工作，为你省下时间与麻烦。而且，由于它是一个由不断壮大的社区（以及 Anthropic 等公司）支持的开放标准，它很可能会成为未来 AI 基础设施的一块基石。

总之，模型上下文协议开启了一个世界：AI 助手不再是孤岛上的天才，而是装备精良的工程师与助手——能够通过统一、安全的接口与众多系统对接、遵循流程、按需获取或创建信息。这是一个强大的愿景，而且正随着 MCP 迅速成为现实。
