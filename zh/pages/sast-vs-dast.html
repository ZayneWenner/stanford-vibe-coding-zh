SAST 与 DAST 与 RASP：对比应用安全测试方法

全球在信息安全上的支出预计到 2025 年将达到 2120 亿美元。这相比 2024 年增长了 15%。根据 Gartner 的说法，生成式 AI 的兴起以及云计算的采用，是这一快速增长的关键原因。该分析机构进一步预测，到 2027 年，生成式 AI 将参与 17% 的网络攻击。

企业需要超越传统方法的先进安全策略，以应对这些日益增长的威胁。这正是企业主需要了解像 SAST、DAST 和 RASP 这类安全解决方案的原因，因为它们为应用提供了多层防护。

（相关阅读： 应用安全详解 与 常见软件测试方法。）

什么是 SAST（静态应用安全测试）？

静态应用安全测试（SAST，Static Application Security Testing）是一种白盒安全测试方法。SAST 利用应用的静态源代码或二进制文件来识别漏洞。这意味着 SAST 工具在应用未运行时，针对应用的代码进行操作。

开发人员使用 SAST 来检测各种安全风险，例如：跨站脚本（XSS）、不安全的反序列化、缓冲区溢出，以及代码中的其他 OWASP 漏洞。由于 SAST 单独无法识别特定于运行时的漏洞，开发人员常常需要将 SAST 与其他测试方法结合使用，以实现全面的安全防护。

SAST 是软件开发生命周期的重要组成部分，因为它能在早期检测漏洞。你发现得越早，修复成本就越低。由于 SAST 工具可以在开发阶段执行，开发人员现在能够在产品上市之前，编写代码并测试上千次（！！）。

SAST 可以集成到 CI/CD 流水线中，集成后被称为“安全 DevOps”或“DevSecOps”。SAST 通过自动化具有极高的可扩展性。能够实施覆盖 SAST 技术的自动化测试，使其成为快速处理代码级风险的高效解决方案。

什么是 DAST（动态应用安全测试）？

动态应用安全测试（DAST，Dynamic Application Security Testing）是一种黑盒测试方法。“动态”一词表明，该方法在应用运行期间评估应用的安全性。与 SAST 不同，DAST 不需要访问应用的源代码。相反，它会：

  1. 模拟外部攻击者的行为。
  2. 从外部测试应用，以识别漏洞——这些漏洞只在运行时才会出现。

DAST 能够识别各种安全缺陷，例如拒绝服务（DoS）漏洞和不安全的服务器配置。通过模拟真实世界的攻击场景，DAST 工具评估应用对这些模拟威胁的响应方式。借助这种方法，开发人员可以发现像 SAST 这类静态测试方法可能遗漏的薄弱环节。

通常，开发人员在软件开发生命周期的后期、往往就在部署前执行 DAST。通过在实时环境中测试应用，DAST 提供对运行时安全的清晰概览，并支持构建能够抵御潜在攻击、性能更佳的应用。

SAST 是如何工作的？

开发人员使用 SAST 工具应用预定义规则和其他检测方法——例如模式匹配和数据分析——来识别编码错误和其他漏洞。他们将这些工具集成到自己的 IDE 或 CI/CD 流水线中，以便在编码和测试阶段自动执行扫描。

常见的 SAST 方法

以下是 SAST 中使用的一些方法。

模式匹配会扫描代码库，寻找不安全的编码实践中的已知模式。例如，使用弱加密算法或不安全的 API 调用。

数据流分析（Data flow C）追踪数据在应用中的流动方式。通过追踪从不可信输入到敏感操作的路径，它可以识别 SQL 注入或缓冲区溢出等漏洞。

控制流分析可以分析应用的控制结构。例如，通过分析循环和条件分支，发现逻辑缺陷或竞态条件等潜在漏洞。

自定义规则创建。许多工具允许开发人员创建自定义规则，以落实编码最佳实践。以下是一些自定义规则的示例：

  • 标记在 SQL 查询中对任何未经过净化的输入的使用。
  • 识别将用户提供的数据未经适当转义就输出到浏览器的代码。
  • 突显易受攻击或已弃用函数的使用，例如 JavaScript 中的 eval() 或 C 语言中的 strcpy()。
  • 检测源代码中出现的硬编码 API 密钥和密码，并标记任何缺少用户输入校验的实例。

依赖项扫描。一些 SAST 工具会分析应用中使用的第三方库和框架，以识别依赖项中的漏洞。

语义分析。通过解释代码的含义而非仅仅其结构，SAST 工具可以检测不安全的配置或 API 的误用。

机器学习模型：先进的 SAST 工具引入了机器学习算法，通过跨大型数据集分析模式，来识别此前未知的漏洞。

使用 SAST 工具时的性能考量

SAST 工具通常需要 大量的 CPU 和内存资源。在分析大型代码库时，这可能是一个重大问题。对一百万行代码做一次完整扫描，可能会消耗数 GB 的内存。

SAST 扫描所需的时间差异极大，取决于代码库的大小，从小型项目的几分钟到企业级应用的数小时不等。这会影响：

  • 构建流水线的进度安排
  • 开发人员生产力

考虑使用支持增量扫描的现代 SAST 工具，让你只分析变更后的代码，而不是整个代码库。

此外，通过规则选择和范围定义进行性能调优至关重要。配置不当的 SAST 工具会不必要地分析非关键代码路径，浪费时间和资源，却无法带来安全收益。

DAST 是如何工作的？

DAST 工具会模拟真实世界的攻击——例如，向输入字段发送各种形式的恶意数据，观察应用如何处理它——以识别应用行为和响应中的漏洞与弱点。

DAST 的步骤

该过程通常涉及以下步骤。

步骤 1：扫描。扫描 Web 应用，发现入口点（例如 URL、表单和 API）。此步骤梳理出应用的结构，并识别潜在的攻击面。

步骤 2：攻击模拟。通过向应用发送精心构造的请求，模拟恶意活动。这些请求通过尝试利用入口点，来测试跨站脚本和跨站请求伪造等漏洞。

步骤 3：漏洞检测。分析应用的响应，以识别安全弱点。它评估应用在遭受攻击时是否如预期般运行。例如，可以注入恶意数据来检测 SQL 注入缺陷。

步骤 4：报告。生成报告，列出检测到的漏洞以及修复建议。开发人员可以利用报告中的结果来修复已识别的问题。

现代 DAST 解决方案可以引入高级特性，例如 AI 驱动的分析和 实时数据集成。它们自动创建测试集，动态地适配应用的结构，并利用机器学习算法将误报降至最低。

使用 DAST 工具时的性能考量

以下是使用 DAST 工具时需要牢记的一些性能瓶颈。

  • DAST 工具会与运行中的应用主动交互，临时增加应用服务器和 Web 服务器上的 CPU 与内存使用率。
  • 扫描期间生成的高并发请求量会消耗大量网络带宽。
  • DAST 扫描器通常会绕过或使应用缓存失效，因为它会生成唯一的请求，从而降低缓存机制的有效性。
  • DAST 工具创建和管理多个测试会话会增加应用服务器的内存使用率。

为避免此类问题或尽可能降低其影响，请遵循以下实践。

  • 在应用使用量最少的非高峰时段安排 DAST 扫描。
  • 在与生产环境配置一致的预发布（staging）或预生产环境中执行扫描。
  • 使用 DAST 工具中的限流（throttling）特性来控制并发请求的数量。
  • 在扫描期间增加应用服务器的线程池。
  • 为 DAST 扫描器 IP 配置独立的缓存策略。
  • 在超过性能阈值时实施自动暂停扫描。

SAST 与 DAST：主要区别

下表总结了 SAST 与 DAST 之间的区别。

标准SASTDAST
测试类型白盒测试。从内部向外测试应用，可访问源代码。黑盒测试。从外部测试应用，无法访问源代码。
支持的软件类型支持各种类型的软件，包括 Web 应用、Web 服务和胖客户端（thick client）。支持 Web 应用和 Web 服务，但通常不支持其他软件类型。
在 SDLC 中的阶段在软件开发生命周期的早期执行。在 SDLC 的后期执行，通常在部署期间或部署之后。
检测到的漏洞识别编码缺陷，例如：SQL 注入、跨站脚本（XSS）、缓冲区溢出等。检测运行时问题，例如服务器配置错误、拒绝服务漏洞以及应用级缺陷。
修复漏洞的成本成本较低，因为问题在 SDLC 早期就被发现。成本更高，因为漏洞被发现得更晚，往往需要及时部署而需要紧急修复。
运行时与环境因素无法检测特定于运行时或与环境因素相关的漏洞。能够识别仅在运行时出现或由于环境因素而产生的漏洞。
深度 vs. 广度对代码级漏洞提供深入的洞察。对应用的外部安全风险提供广泛的视角。
与工具的集成与 IDE 和 CI/CD 流水线集成，实现自动化的静态分析。与 CI/CD 流水线集成，实现持续的运行时测试。
误报与漏报由于深入的代码分析，误报概率较高。误报较低，但由于内部可见性有限，漏报风险更高。
技术依赖依赖 编程语言和框架；需要与工具兼容。独立于应用框架，因为它们从外部与应用交互。

SAST 与 DAST 的优缺点

SAST 的优点

  • 在软件开发生命周期的早期识别安全漏洞。
  • 分析代码库，包括基础函数与复杂的分支。
  • 直接在源代码上操作，无需应用运行。
  • 提供带有全面洞察的实时反馈，例如漏洞的确切位置。
  • 生成可导出的报告，可使用仪表盘进行跟踪。
  • 支持自动化，因此比人工代码审查更快、更高效。

SAST 的缺点

  • 常常产生大量误报。因此，可能需要人工审查。
  • 无法识别特定于运行时或环境的漏洞，例如配置错误。
  • 需要针对每种编程语言专用的工具，因此维护复杂。
  • 难以理解外部库、API 和 REST 端点。

DAST 的优点

  • 识别仅在应用执行期间出现的漏洞。
  • 从外部操作，无需访问源代码。这对于测试第三方应用或编译后的代码很有效。
  • 模拟真实的攻击场景，识别 SAST 遗漏的风险。
  • 独立于应用的编程语言工作。
  • 评估整个应用和系统。这包括内存消耗、资源使用以及第三方接口。

DAST 的缺点

  • 只关注应用的外部层，可能遗漏更深层中的漏洞。
  • 应用于 SDLC 的后期，因此修复成本更高、更耗时。
  • 会漏掉 SAST 工具可以通过源代码分析识别的某些漏洞。例如，考虑一个 Web 应用使用不安全的随机数生成器（例如 JavaScript 中的 Math.random()）来创建会话令牌。DAST 可能会遗漏这一缺陷，因为它只测试运行时行为。（但 SAST 可以检测到它。）
  • 大型项目需要自定义基础设施，并需要应用的多个实例并行运行，因此是资源密集型的。

我应该在何时使用 SAST 与 DAST？

SAST 和 DAST 在保障 SDLC 安全方面扮演着互补的角色。了解何时使用哪一种，有助于实现全面的安全覆盖。

何时使用 SAST

在早期开发阶段。开发人员使用 SAST，在 SDLC 早期识别 SQL 注入和硬编码凭据等漏洞。通过在部署前捕获这些问题，他们降低了修复的成本和复杂度。

例如：一个 SAST 工具扫描 Python 代码，并标记出源代码中嵌入了硬编码 API 密钥的漏洞。开发人员重构代码，使用环境变量来安全地存储和检索这些密钥。

用于代码审查。SAST 集成到版本控制系统中。允许开发人员在提交代码之前扫描其代码。这确保只有安全的代码进入代码仓库。

示例：SAST 工具可以检测到文件路径直接由未经校验的用户输入构造、使应用暴露于路径遍历攻击的漏洞。开发人员通过净化输入并使用安全的库函数处理文件路径来修复该问题。

在持续集成/持续部署流水线中。SAST 在 CI/CD 过程中运行自动化扫描。它为开发人员提供实时反馈。

何时使用 DAST

预生产测试。开发人员使用 DAST，在预发布（staging）或 QA 环境中识别运行时漏洞（例如：不安全的配置、认证缺陷、访问控制不足）。

示例：DAST 工具可以检测导致敏感数据暴露的数据库配置错误。然后开发人员可以在部署前保护该配置。

部署后监控。DAST 工具持续扫描已部署的应用，以发现由环境变化或新出现的威胁导致的漏洞。这保证了应用长期保持安全。

测试第三方集成。DAST 可以模拟外部攻击者的视角，来识别第三方 API 或互连系统中的漏洞。

例如：DAST 工具测试一个 Web 应用，发现第三方支付 API 中存在漏洞——信用卡信息正通过未加密的 HTTP 连接传输。开发人员通过强制所有 API 通信使用 HTTPS 来解决问题。

哪个更有效：SAST 还是 DAST？

SAST 或 DAST 的有效性取决于：

  • SDLC 所处的阶段
  • 所处理漏洞的类型

SAST 在开发早期效果最佳，主要用于识别源代码中的漏洞、降低成本并促进安全的编码实践。相比之下，DAST 侧重于预生产或已部署应用中的运行时漏洞。它提供关于配置错误和不安全集成等问题的洞察。

采用混合方法

与其二选一，将 SAST 与 DAST 结合，可以创建一种多层安全策略，同时覆盖静态代码和运行时环境中的漏洞。SAST 可以集成到早期开发阶段，在应用编译前检测并修复代码级问题。一旦应用在测试环境中运行起来，DAST 就可以识别运行时漏洞，并评估应用在遭受攻击时的行为。

在 CI/CD 流水线中自动化 SAST 和 DAST 扫描，可在不牺牲安全性的前提下提供持续反馈并加速开发过程。

对于敏捷或 DevOps 环境，添加像 IAST 或 RASP 这样的工具可以进一步加强安全性。通过关联 SAST 和 DAST 的结果，组织可以实现更全面、更有效的漏洞管理。

将 RASP 作为 SAST 和 DAST 的替代方案

运行时应用自我防护（RASP，Runtime Application Self-Protection）是一种直接安装在应用运行的 服务器上的高级安全解决方案。

RASP 将自己嵌入应用的运行时环境中。这种集成使 RASP 能够分析应用的逻辑和数据。在分析的同时，它可以：

  1. 在异常行为发生时检测到它们。
  2. 立即阻断恶意活动。

一个关键区别在于，RASP 不只是对潜在问题发出警报——它会通过隔离和解决威胁、而不依赖外部工具，来主动阻止攻击。

RASP 提供了 SAST 和 DAST 的一种动态替代方案。与 SAST 分析静态代码、DAST 模拟外部攻击不同，RASP 实时运行。它在执行期间监控应用的行为，并通过终止会话或向防御者发出警报来响应实时威胁。

RASP 在保护应用免受绕过网络防御或在开发过程中被遗漏的漏洞方面特别有效。

然而，对 RASP 的过度自信可能导致组织忽视安全的编码实践。此外，由于 RASP 直接在应用的运行时环境中运行，它可能会影响应用性能。RASP 无法取代修复底层缺陷的需要，但在修复工作进行期间，它提供了持续的保护。

正如 一位 RASP 用户所评论的：

“是否决定使用 RASP 工具，应基于对应用特定需求与风险状况的透彻评估。”

未来属于结合 SAST、DAST 和 RASP 的应用安全测试

应用测试的未来在于结合 SAST、DAST 和 RASP，以创建全面的安全策略。随着安全挑战的增长，将这些工具集成到 CI/CD 流水线中并自动化其流程将变得必不可少。

AI 和机器学习的进步将使测试更高效，因为它有助于减少误报并改进威胁检测。

金融与 FinServ 行业

在金融领域，AI 驱动的工具将改变漏洞被检测和缓解的方式。SAST 和 DAST 将继续在开发和预生产阶段识别编码缺陷与运行时问题。

但你不会止步于此：RASP 会走得更远，利用 AI 来监控实时交易。例如，RASP 可以检测异常模式（例如：攻击者试图实时利用某个漏洞），并在通知安全团队的同时阻断这些活动。

IoT、边缘与联网设备

在 IoT 方面，这些工具的组合将在保护联网设备方面发挥重要作用。方式如下：

  • SAST 可以在开发期间确认固件没有漏洞。
  • DAST 可以测试设备之间通信协议的安全性。
  • 与此同时，RASP 监控已部署的设备，检测并阻止由新出现的威胁导致的未授权访问尝试或数据泄露。

同样地，使用多种方法将有助于 IoT 生态系统保持韧性。正如我们在许多示例中解释的那样，SAST、DAST 和 RASP 共同预示着一个未来——应用将以更强大、更主动的安全措施被构建和部署。

韧性安全始于主动测试

将 SAST、DAST 和 RASP 结合在一起，可以提供覆盖整个软件开发生命周期的稳健安全。

通过将这些方法集成到 CI/CD 流水线中，并利用 AI 的进步，组织可以主动应对新出现的威胁。这些方法共同提供了一种整体的方法，来保护现代应用免受安全漏洞的侵害。
