为智能体编写高效的工具——借助智能体

发布于 2025 年 9 月 11 日

智能体（agent）的效力，只能达到我们赋予它们的工具所允许的程度。我们在此分享如何编写高质量的工具与评测（evaluation），以及如何通过让 Claude 为其自身优化工具来提升性能。

模型上下文协议（MCP）可以让大语言模型（LLM）智能体获得多达数百个工具来解决现实世界的任务。但我们如何让这些工具发挥出最大的效力？

在这篇文章中，我们描述了我们在多种智能体式（agentic）AI 系统中提升性能的最有效技巧1。

我们从介绍你可以如何做到以下几点开始：

  • 构建并测试你的工具原型
  • 用智能体创建并运行对你工具的综合评测
  • 与像 Claude Code 这样的智能体协作，自动提升你工具的性能

最后我们给出在此过程中总结出的、编写高质量工具的关键原则：

  • 选择要（以及不要）实现哪些正确的工具
  • 对工具进行命名空间（namespacing）划分，以界定清晰的功能边界
  • 从工具向智能体返回有意义的上下文
  • 针对 Token 效率优化工具响应
  • 对工具的描述与规约进行提示工程（prompt engineering）

构建一份评测，能让你系统地度量工具的性能。你可以借助 Claude Code 针对这份评测自动优化你的工具。

什么是工具？

在计算中，确定性系统（deterministic systems）在给定相同输入时每次都产生相同输出，而非确定性系统——比如智能体——即便起始条件相同，也可能产生不同的响应。

当我们传统地编写软件时，我们是在确定性系统之间建立一份契约。例如，像 getWeather("NYC") 这样的函数调用，每次被调用时都会以完全相同的方式去获取纽约市的天气。

工具是一种新型的软件，它体现的是确定性系统与非确定性智能体之间的契约。当用户问"我今天该带伞吗？"时，一个智能体可能会调用天气工具、从通用知识中作答，甚至先就地点提出一个澄清性问题。偶尔，智能体可能会幻觉（hallucinate），甚至没能弄懂如何使用一个工具。

这意味着，在为智能体编写软件时，我们需要从根本上重新思考我们的方法：我们不应像为其他开发者或系统编写函数和 API 那样去编写工具和 MCP 服务器，而是需要为智能体而设计它们。

我们的目标，是通过让智能体运用工具去追求各种成功的策略，来扩大智能体能够有效解决广泛任务的"表面积（surface area）"。幸运的是，根据我们的经验，那些对智能体而言最"顺手（ergonomic）"的工具，最终对人类来说也出奇地直观易懂。

如何编写工具

在本节中，我们描述你可以如何与智能体协作，既去编写、也去改进你交给它们的工具。先从快速搭建一个工具原型并在本地测试开始。接着，运行一次全面的评测来衡量后续的改动。与智能体并肩工作，你可以反复进行评估与改进工具的循环，直到你的智能体在现实任务上取得强劲表现。

构建原型

如果不亲自上手，往往难以预见哪些工具对智能体而言是顺手的、哪些不是。先从快速搭建一个你的工具原型开始。如果你正在使用 Claude Code 来编写你的工具（可能是一次性完成），给 Claude 提供你的工具所依赖的任何软件库、API 或 SDK（其中可能也包括 MCP SDK）的文档会很有帮助。对 LLM 友好的文档，通常可以在官方文档站点上以扁平的 llms.txt 文件形式找到（这是我们 API 的示例）。

将你的工具包装进一个本地 MCP 服务器或桌面扩展（DXT），可以让你在 Claude Code 或 Claude Desktop 应用中连接并测试你的工具。

要将你的本地 MCP 服务器连接到 Claude Code，运行 claude mcp add [args...]。

要将你的本地 MCP 服务器或 DXT 连接到 Claude Desktop 应用，请分别进入 Settings > Developer 或 Settings > Extensions。

工具也可以直接传入 Anthropic API 调用中进行编程式测试。

你自己去测试这些工具，以识别任何粗糙的边缘。从你的用户那里收集反馈，从而围绕你期望工具所能支撑的使用场景和提示（prompt）建立起直觉。

运行评测

接下来，你需要通过运行评测来衡量 Claude 使用你的工具的表现。先从生成大量基于真实世界用途的评测任务开始。我们建议与一位智能体协作，帮助分析你的结果并确定如何改进你的工具。在我们的工具评测实战手册（tool evaluation cookbook）中可以看到这一过程的端到端展示。

生成评测任务

借助你的早期原型，Claude Code 可以快速探索你的工具，并创建出数十对提示与响应。提示应当受到真实世界用途的启发，并基于现实的数据源与服务（例如内部知识库和微服务）。我们建议你避免过于简单或肤浅的"沙箱（sandbox）"环境，那种环境无法以足够的复杂度来压力测试你的工具。一个有力的评测任务可能需要多次工具调用——可能是几十次。

以下是一些有力任务的例子：

  • 下周与 Jane 安排一次会议，讨论我们最新的 Acme Corp 项目。附上我们上次项目规划会议的笔记，并预订一间会议室。
  • 客户 ID 9182 报告说，他们因一次购买尝试而被重复扣款三次。找出所有相关的日志条目，并判断是否有其他客户受到同一问题影响。
  • 客户 Sarah Chen 刚刚提交了取消请求。准备一份挽留方案。确定：（1）他们为什么要离开，（2）哪种挽留方案最具吸引力，（3）在给出方案前我们应当留意哪些风险因素。

以下是一些较弱任务的例子：

  • 下周与 jane@acme.corp 安排一次会议。
  • 在支付日志中搜索 purchase_complete 和 customer_id=9182。
  • 通过客户 ID 45892 找到取消请求。

每个评测提示都应当配上一个可验证的响应或结果。你的验证器（verifier）可以简单到在真实答案（ground truth）与采样响应之间做精确字符串比较，也可以高级到请 Claude 来评判响应。要避免过于严格的验证器，因为它们会因为格式、标点或合理的替代措辞等虚假差异而拒掉正确的响应。

对于每一对提示-响应，你还可以选择性地指定你期望智能体在解决该任务时调用的工具，以衡量智能体在评测中是否成功把握了每个工具的目的。然而，由于可能存在多种正确的解题路径，要尽量避免过度指定或对策略过拟合。

运行评测

我们建议通过直接的 LLM API 调用来以编程方式运行你的评测。使用简单的智能体式循环（用 while 循环包裹交替进行的 LLM API 调用与工具调用）：每个评测任务对应一个循环。每个评测智能体都只应被给定一个任务提示和你的工具。

在评测智能体的系统提示（system prompt）中，我们建议指示智能体不仅输出结构化的响应块（用于验证），还要输出推理（reasoning）和反馈（feedback）块。指示智能体在工具调用块和响应块之前输出这些内容，可以通过触发思维链（Chain-of-Thought，CoT）行为来提升 LLM 的有效智能。

如果你是用 Claude 运行评测，可以开启交织式思考（interleaved thinking）来获得类似功能，"开箱即用"。这会帮助你探查智能体为何调用或为何不调用某些工具，并突显出工具描述与规约中需要改进的具体环节。

除了顶层准确率之外，我们建议收集其他指标，例如单个工具调用与任务的总运行时间、工具调用的总次数、Token 的总消耗量，以及工具错误。追踪工具调用有助于揭示智能体所追求的常用工作流，并为工具整合（consolidate）提供一些机会。

分析结果

智能体是你发现问题和提供反馈的有益伙伴，反馈范围涵盖从相互矛盾的工具描述，到低效的工具实现，再到令人困惑的工具模式（schema）。不过请记住，智能体在其反馈与响应中省略的内容，往往比它们包含的内容更重要。LLM 并不总是说出它们的真实意思。

观察你的智能体在哪些地方卡住或感到困惑。通读你的评测智能体的推理与反馈（或 CoT）来识别粗糙的边缘。审阅原始记录（包括工具调用与工具响应），以捕捉任何未在智能体 CoT 中明确描述的行为。要读懂言外之意；请记住，你的评测智能体未必知道正确答案与策略。

分析你的工具调用指标。大量冗余的工具调用，可能意味着有必要对分页（pagination）或 Token 上限参数做一些适度调整；针对无效参数的大量工具错误，可能意味着工具可以使用更清晰的描述或更好的示例。当我们发布 Claude 的网页搜索工具时，我们发现 Claude 会不必要地把 2025 附加到该工具的查询参数上，这会让搜索结果产生偏差并降低性能（我们通过改进工具描述，把 Claude 引向了正确的方向）。

与智能体协作

你甚至可以放手让智能体来分析你的结果，并为你改进你的工具。只需把来自你评测智能体的记录拼接起来，粘贴进 Claude Code 即可。Claude 在分析记录、一次性重构大量工具方面是专家——例如，为了确保在进行新的改动时工具实现与描述保持自洽。

事实上，本文中的大部分建议，都来自我们用 Claude Code 反复优化内部工具实现的过程。我们的评测建立在内部工作区之上，模拟了我们内部工作流的复杂度，包括真实的项目、文档和消息。

我们依赖留存（held-out）测试集，以确保我们没有对我们的"训练"评测过拟合。这些测试集揭示出，即便在"专家级"工具实现的基础上，我们仍能提取出额外的性能提升——无论那些工具是由我们的研究员手动编写的，还是由 Claude 本身生成的。

在下一节中，我们将分享我们从这一过程中学到的一些东西。

编写高效工具的原则

在本节中，我们将所学提炼为编写高效工具的几条指导性原则。

为智能体选择合适的工具

更多的工具并不总带来更好的结果。我们观察到一个常见的错误，是那些仅仅包装了既有软件功能或 API 端点的工具——无论这些工具是否适合智能体。这是因为智能体相对于传统软件有着不同的"可供性（affordances）"——也就是说，它们感知可用动作的方式不同。

大语言模型（LLM）智能体拥有有限的"上下文"（也就是说，它们一次能处理的信息量是有限的），而计算机内存既便宜又充裕。考虑在通讯录中搜索联系人的任务。传统软件程序可以高效地、一次一个地存储和处理联系人列表，在继续之前逐个检查。

然而，如果一个 LLM 智能体使用一个返回所有联系人、然后不得不逐 Token 地通读每一个的工具，它就是在用其有限的上下文空间浪费在无关信息上（想象一下，你是通过从头到尾逐页阅读来在通讯录中搜索一个联系人——也就是通过暴力搜索）。对智能体和人类而言都更好、更自然的方法是先跳到相关页面（或许按字母顺序找到它）。

我们建议构建少量精心设计、针对特定高影响力工作流的工具，这些工具要与你的评测任务相匹配，并由此向上扩展。在通讯录的例子中，你可能会选择实现一个 search_contacts 或 message_contact 工具，而不是一个 list_contacts 工具。

工具可以整合功能，在底层处理可能多个离散的操作（或 API 调用）。例如，工具可以用相关的元数据来丰富工具响应，或在一次工具调用中处理频繁被串联起来的多步任务。

以下是一些例子：

  • 不要实现 list_users、list_events 和 create_event 这几个工具，而是考虑实现一个 schedule_event 工具，它负责查找空闲时间并安排一个事件。
  • 不要实现 read_logs 工具，而是考虑实现一个 search_logs 工具，它只返回相关的日志行以及一些周边上下文。
  • 不要实现 get_customer_by_id、list_transactions 和 list_notes 这几个工具，而是实现一个 get_customer_context 工具，它一次性编译出某个客户所有近期且相关的信息。

确保你构建的每一个工具都有清晰、独特的用途。工具应当让智能体能够像人类在获得相同底层资源 access 时那样，去细分并解决任务，同时减少本会被中间输出所消耗的上下文。

过多的工具或相互重叠的工具，也会让智能体分心，无法追求高效的策略。对你所构建（或不构建）的工具进行谨慎、有选择性的规划，真的会有回报。

对工具进行命名空间划分

你的 AI 智能体可能会获得对几十个 MCP 服务器和数百个不同工具的访问——其中包括其他开发者的工具。当工具在功能上重叠或目的含糊时，智能体会对到底该用哪个感到困惑。

命名空间（namespacing，把相关工具归在共同前缀下）有助于在大量工具之间划清边界；MCP 客户端有时会默认这样做。例如，按服务对工具命名空间划分（如 asana_search、jira_search）以及按资源划分（如 asana_projects_search、asana_users_search），可以帮助智能体在正确的时机选择正确的工具。

我们发现，在基于前缀与基于后缀的命名空间之间做选择，会对我们的工具调用评测产生不小的影响。效果因 LLM 而异，我们鼓励你根据自己的评测来选择命名方案。

智能体可能会调用错误的工具、用错误的参数调用正确的工具、调用过少的工具，或错误地处置工具响应。通过有选择地实现那些名称能反映任务自然细分的工具，你同时减少了加载进智能体上下文的工具数量与工具描述，并把智能体式计算从智能体上下文中卸载回工具调用本身。这降低了智能体犯错的的整体风险。

从工具向智能体返回有意义的上下文

同理，工具实现应当注意，只把高信号的信息返回给智能体。它们应当优先考虑上下文相关性而非灵活性，并避开低层的技术标识符（例如：uuid、256px_image_url、mime_type）。像 name、image_url 和 file_type 这样的字段，更有可能直接指导智能体的下游动作与响应。

智能体处理自然语言名称、术语或标识符，往往比处理晦涩的标识符要成功得多。我们发现，仅仅把任意的字母数字 UUID 解析为语义上更有意义、更可解释的的语言（甚至是一个从 0 开始的 ID 方案），就能通过减少幻觉来显著提升 Claude 在检索任务中的精确度。

在某些情况下，智能体可能需要灵活性，既能与自然语言交互，也能与技术标识符输出交互，哪怕只是为了触发下游的工具调用（例如，search_user(name='jane') → send_message(id=12345)）。你可以通过在工具中暴露一个简单的 response_format 枚举参数来同时支持两者，让你的智能体去控制工具返回"简洁（concise）"还是"详细（detailed）"的响应（见下图）。

你可以添加更多格式以获得更大的灵活性，类似于 GraphQL，你可以精确选择想要接收的哪些信息片段。下面是一个用于控制工具响应冗长程度的 ResponseFormat 枚举示例：

  DETAILED = "detailed",
  CONCISE = "concise"

针对 Token 效率优化工具响应

优化上下文的质量很重要。但优化工具响应中返回给智能体的上下文的数量同样重要。

我们建议对任何可能消耗大量上下文的工具响应，实现分页、范围选择、过滤和/或截断的某种组合，并配以合理的默认参数值。对于 Claude Code，我们默认将工具响应限制在 25,000 个 Token。我们预计智能体的有效上下文长度会随时间增长，但对上下文高效工具的需求将会持续。

如果你选择截断响应，请务必用有帮助的说明来引导智能体。你可以直接鼓励智能体追求更具 Token 效率的策略，例如在知识检索任务中，做许多小而精准的搜索，而不是一次宽泛的搜索。类似地，如果一个工具调用引发了错误（例如在输入校验期间），你可以通过提示工程来设计你的错误响应，清晰地传达具体且可操作的改进建议，而不是给出不透明的错误码或回溯（traceback）。

对工具描述进行提示工程

现在我们来到改进工具最有效的方法之一：对你的工具描述和规约进行提示工程。由于这些内容会被加载进智能体的上下文，它们能够集体引导智能体走向有效的工具调用行为。

在编写工具描述和规约时，想一想你会如何向你团队里的一名新员工描述你的工具。考虑你可能隐含地带入的上下文——专门的查询格式、小众术语的定义、底层资源之间的关系——并使之显式化。通过清晰描述（并用严格的数据模型强制执行）预期的输入与输出，来避免歧义。尤其要给输入参数起无歧义的名字：与其使用一个名为 user 的参数，不如尝试一个名为 user_id 的参数。

借助你的评测，你可以更有把握地度量提示工程的影响。即便是对工具描述很小的改进，也能带来显著的提升。在我们针对工具描述做了精确的改进之后，Claude Sonnet 3.5 在 SWE-bench Verified 评测上取得了最先进的（state-of-the-art）性能，大幅降低了错误率并提升了任务完成度。

你可以在我们的开发者指南中找到工具定义的其他最佳实践。如果你正在为 Claude 构建工具，我们还建议阅读关于工具如何被动态加载进 Claude 的系统提示的内容。最后，如果你正在为一个 MCP 服务器编写工具，工具注解（tool annotations）有助于披露哪些工具需要开放世界（open-world）访问权限或会做出破坏性改动。

展望

要为智能体构建高效的工具，我们需要将软件开发实践从可预测的、确定性的模式，重新定向到非确定性的模式。

通过我们在本文中描述的、迭代的、由评测驱动的过程，我们已经识别出关于什么让工具成功的、一贯的模式：高效的工具是被有意识且清晰地定义的，审慎地使用智能体上下文，能够在多样的工作流中相互组合，并让智能体能够直观地解决现实世界的任务。

未来，我们预计智能体与世界交互的具体机制会不断演化——从 MCP 协议的更新，到底层 LLM 自身的升级。借助系统化的、由评测驱动的方法来改进面向智能体的工具，我们可以确保：随着智能体变得更有能力，它们所使用的工具也会随之演化。
