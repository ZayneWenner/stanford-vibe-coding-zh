使用 Claude Code 与 OpenAI Codex 在现代 Web 应用中发现漏洞

我们对 AI 编程智能体（Coding Agent）发现漏洞能力的深度调研，揭示了令人惊讶的优势、关键的弱点，以及一个严重的"一致性"问题。

作者：Romain Gaucher、Vasilii Ermilov、Clint Gibler · 2025 年 9 月 2 日

内容提要（TL;DR）

我们评估了 AI 编程智能体在真实代码中查找漏洞的有效性。

  • 方法：我们让 Anthropic 的 Claude Code（v1.0.32，Sonnet 4）和 OpenAI Codex（v0.2.0，o4-mini）在 11 个流行且庞大的开源 Python Web 应用中查找漏洞。它们一共产生了 400 多条安全发现，由我们的安全研究团队逐一审查。
  • AI 编程智能体能找到真实的漏洞：Claude Code 发现了 46 个漏洞（真阳性率 TPR 14%、假阳性率 FPR 86%），Codex 报告了 21 个漏洞（TPR 18%、FPR 82%）。其中约 20 个是高严重性漏洞。
  • AI 能把握上下文，却在"数据流"上卡壳：Claude Code 最擅长发现不安全的直接对象引用（IDOR）缺陷，真阳性率达 22%（13 个正确/59 个报告），但在跨多个文件与函数做污点追踪（taint tracking）时表现吃力——SQL 注入 TPR 仅 5%（2/38），XSS 为 16%（12/74）。OpenAI Codex 在报告正确的 IDOR 上完全失败，TPR 为 0%（0/5），SQL 注入 0%（0/5）、XSS 0%（0/28），但令人意外地在路径遍历上报告的正确数量多于 Claude Code，TPR 达 47%（8/17）。
  • 非确定性是个真问题：在相同代码库上对完全相同的提示多次运行，结果往往大相径庭。在某一个应用中，三次相同运行的发现数分别是 3、6、11 条。

核心结论：

  • 只需相对简单的、聚焦安全的提示，AI 编程智能体就已经能在真实应用中发现真实漏洞。
  • 但是：取决于漏洞类型，结果可能相当嘈杂（假阳性率高），尤其是在 SQL 注入、XSS、SSRF 这类传统"注入式"漏洞类别上。
  • 详尽的评估与基准测试，对于理解某种方法在发现漏洞上到底有多有效至关重要（这一点始终成立，但在 Claude Code、Codex 这类非确定性工具面前，重要性更甚），也能让你知道自己的改进是否走在正确的方向上。
  • 这是我们关于"使用并增强 AI 来发现漏洞"系列文章的第一篇！

本文涵盖：

  • 常用 SAST 基准测试的问题，以及它如何影响 AI SAST 评估；
  • 关于基于 AI 的漏洞搜寻的一些开放研究问题；
  • 我们的 AI 编程智能体实验、数据集，以及我们学到了什么；
  • Anthropic 的 /security-review 命令为何表现平平；
  • AI 编程智能体的非确定性，以及它为何发生。

引言

在 Semgrep，我们就靠应用安全（AppSec）吃饭。我们很早就将 AI 投入生产（Assistant 背后的技术、用 promptfoo 测试我们的 AI 工作流、用安全研究员的分诊结果来评估自动分诊表现），并持续研究如何把传统的、确定性的分析与现代 AI 的上下文能力做最佳组合，而不是盲目追潮流。

这项研究正是这一长期使命的一部分。我们开启了一场公开、深入的探索，来回答一个大家都关心的问题：LLM 在源码中找漏洞到底有多有效？

关于基于 AI 的漏洞搜寻的开放研究问题

为了引导我们的调研，我们把"LLM 擅长找 bug 吗？"这个宽泛的问题，拆成了更具体、可度量的子问题：

  • 基于 LLM 的漏洞发现，其假阳性率与假阴性率是多少？是否会因编程语言、框架、代码库规模或漏洞类别而异？对代码的写法有多敏感？
  • 假阳性与假阴性的常见原因是什么？
  • 分析有多确定？每次都能得到相同结果吗？

针对注入类漏洞，我们特别想了解：

  • LLM 在"源"（例如用户传入的值）与"汇聚点"（sink，例如消费原始 SQL 查询的方法）之间追踪用户输入的有效性如何？
  • 它能跨函数、跨文件追踪数据吗？
  • 它能推理出净化（sanitization）函数和其他安全控制吗？
  • 它能推理出第三方开源依赖中的函数吗？

常用 SAST 基准测试的问题：缺乏现实性

在深入我们的发现之前，先聊聊我们如何衡量 AI 的表现。目前大量的研究/宣称都依赖基准测试——它们固然有价值，却未能充分体现真实世界代码的复杂性。

  • 带已知漏洞的应用：这些基准只使用带有已知漏洞的开源应用，其中许多可以在 vulnerable-apps 找到（感谢 Kinnaird McQuade）。如果你读过这个博客，可能认得一些名字：WebGoat、JuiceShop、OWASP Benchmark 等。但它们有个问题：当前的 LLM 很可能已经"吞下"了这些仓库的代码，以及互联网上大量公开的剖析文章，从而具备先验知识、扭曲了结果。它们的代码往往不具现实性——过多的注释、注解和变量名会暗示甚至直接描述漏洞在哪里、如何利用。有时，工具结果甚至被直接提交进了仓库。
  • XBOW 基准：XBOW 为自动化渗透测试工具提供了基准，但并不适配静态分析：代码常常过于刻意、过于简单，无法代表真实应用。ZeroPath 在清理它们方面做得不错，但只有一小部分被清理过。此外，这些测试用例都是微型应用，专门用来触发某个特定的攻击场景。以 Python 基准为例，XBOW 有 45 个——45 个各不相同的微型应用，平均不到 98 行代码、3 个 Python 文件。这太小了，无法承载在完整代码库或众多函数中进行搜索与推理的复杂性。
  • CVE 记忆偏差：由于 LLM 是在来自互联网的海量公开数据上训练的，其中就包括那些发现并修复了 CVE 的代码库本身。这造成了一个根本性的数据污染问题。AI 可能不是通过新颖的分析发现漏洞，而只是识别出了它在训练时"背下来"的模式。

最近，学术界设计了 CyberGym、Eyeballvul、SecVulEval 等基准。它们显示出很大进步，也更接近真实世界的例子，但缺少对现代 Web 应用的聚焦，或把漏洞从更广阔的应用上下文中孤立了出来。

  • EyeballVul：Timothée Chauvin 近期提出的基准，从开源项目中抽取经过人工审核的真实漏洞，并以最小的、可复现的测试用例形式呈现。虽然基于真实代码，它仍然把漏洞从广阔的应用上下文中孤立出来，让"搜索"问题变得更简单。
  • SecVulEval 与 CyberGym：这些套件用于评估 C 或 C++ 中的漏洞。虽然在各自领域很有价值，但它们聚焦 C/C++，意味着这些数据并不适用于主导现代云原生开发的 Python/JavaScript 等以 Web 为中心的语言。

尽管上述每种方法都有用、某些时候应当采用，但它们未必反映现代软件开发的现实。真实世界的应用不是干净、孤立的函数。它们是依赖、框架和业务逻辑交织成的复杂网络。

我们的方法不同。我们在 11 个庞大的、基于 Python、 actively maintained 的开源项目上做测试，这些项目使用常见的 Web 框架（Django、Flask、FastAPI）。我们的方法是对前述方法的补充，并且我们相信它的独特之处在于：(a) 旨在代表真实世界中由 AI 驱动的漏洞发现（而非小型、孤立的合成样例）；(b) 未被模型训练数据污染；(c) 代表了大多数开发者和公司实际在构建的应用类型——使用现代语言与框架的 Web 应用。

本文的研究范围

为了让问题可解，我们聚焦于：

  • 开箱即用地使用一次 Anthropic Claude Code（v1.0.32，Sonnet 4）和 OpenAI Codex（v0.2.0，o4-mini），采用一个简单的、脚本化的提示 [1] 复用于不同种类的漏洞。我们要求它们返回 SARIF 格式的安全问题。

我们的发现

  • Claude Code 和 Codex 今天都很有用：它们能发现真实的安全漏洞，但非常嘈杂。整体噪声仍然很高，但它们确实在这些流行的开源 Python Web 应用中发现了真实的安全漏洞。总体而言，Claude Code 发现了 46 个漏洞（TPR 14%、FPR 86%），Codex 报告了 21 个漏洞（TPR 18%、FPR 82%）。
  • 许多 IDOR 缺陷初看都"像真的"，且 Claude Code 还提出了可信的修复方案：LLM 不仅能发现这些 bug，还能提出可信的修复——例如基于代码中已有的模式注入新的权限检查。IDOR 问题往往难以分诊，我们不得不对其中大多数做实际测试才能确定，这也把真阳性率拉低了不少。
  • Claude Code 能当作不错的"安全护栏"工具吗？许多发现虽然技术上属于假阳性，却仍是很好的"护栏"建议，或看上去像那么回事。例如，模型常常建议把一段已经安全的 SQL 查询参数化。这虽然不算漏洞，却加固了代码。我们仍然把这些算作假阳性，尽管没那么严重。不过，这些代码加固建议并不总是可信。我们发现了好几处——尤其是在客户端 JavaScript 代码中——AI 试图"修复"它认为围绕 DOM 操作存在的问题，结果反而破坏了代码（在我们观察到的案例中，对 HTML 做了双重转义），而那里本来根本没有安全问题。
  • XSS 与 SQL 注入——很难把组件拼到一起：模型难以把数据从服务端框架追踪到客户端组件（XSS 的常见模式），或穿过复杂的应用层。它常常被静态定义的数据搞混，或无法识别服务端侧的净化处理。
  • 重复提示有助于得到更多结果：LLM 的概率性本质意味着，用略有差异的方式问同一个问题，可能得到新的发现，这凸显了分析的不一致性。在同一代码库上重复相同的提示会得到不同的答案，但最后往往又会绕回到相同的发现上。
  • OpenAI Codex 有时无法输出有效的 SARIF：在预期 66 份报告中，有 9 份不是有效的 SARIF。我们考虑了这些文件中报告的所有发现，但它们既非有效 SARIF 也非有效 JSON。Claude Code 在我们尝试的所有案例中都没有这个问题。

同样的代码、同样的 AI、每次不同的 bug：AI 编程智能体的非确定性问题

为了探索非确定性在实践中如何体现，我们选了其中三个应用，用同一个提示、针对同一个安全问题（IDOR）多次运行。一个规律浮现出来：每次运行，AI 的发现都不一样。

在漏洞检测的语境下，这是个严重问题。首先，作为安全工程师，我们理想情况下希望能对"重要漏洞类别是否已被扫描"有更强的保证，而不是"我希望这次模型搜索得够彻底"。

其次，间歇性地检测到漏洞，会造成你的安全工具或漏洞管理系统出现不一致和噪声。例如，如果你使用的是 SAST 平台、ASPM，或内部自建的系统，这些系统通常假设：当一个之前检测到的漏洞不再出现时，它已经被修复了。但在 LLM 驱动的检测中未必如此——单次扫描可能漏掉它，于是当后续扫描重新发现同一个问题时，就会创建一条"新"的发现，导致重复的 JIRA 工单和开发者的不满。

以下是我们观察到的一些具体例子：

  • PY-APP-007：第一次运行时，AI 识别出一个"缺失的搜索授权"漏洞，而另外两次运行都没有。第二次运行标记了仅属于那一次的问题。第三次运行则发现了它自己独有的一组漏洞。
  • PY-APP-006：类似的故事：第一次运行在用户 API 中挖出一个漏洞，而后续运行聚焦在代码库的不同部分，比如事件摘要和笔记模块。
  • PY-APP-002：这里的可变性或许最为显著。被发现漏洞的数量从第一次运行的 3 个，跳到第二次的 6 个，再到第三次的 11 个。每次运行呈现的发现都只是部分重叠。

那么，背后的原因是什么？我们相信关键因素在于所谓的上下文退化（context rot）和压缩（compaction）。当一个 AI 智能体被要求分析整个代码库时，它要处理海量信息：上下文退化导致它无法准确地从自身上下文中检索内容。为了应对这一点，LLM 使用了一种有损压缩（有时称作 compaction），意味着一些更细的推理细节——比如函数名、路径等——可能在摘要过程中丢失。

这就像试图概括一部长而复杂的小说。你会抓住主要情节，但难免会漏掉一些微妙和细腻之处。同样地，AI 可能丢失对某个特定架构模式或细微数据流的追踪，导致它在某次运行中漏掉一个漏洞，而在另一次运行中又能抓到。我们在 PY-APP-006 中看到了一个清晰的例子：AI 提出的一个修复方案不完整，因为它没能复用已有的、用于用户授权的基类——一个关键的上下文，在那次特定运行中似乎丢失了。

这种非确定性对我们如何对待"AI 原生的 SAST"有着重大意义。一方面，AI 每次"思考"方式不同，意味着它能探索更广泛的潜在攻击向量，很像一支拥有多元视角的人类渗透测试团队。另一方面，它引入了一层不确定性，可能导致困惑或误判。

  • 覆盖不完整：单次运行可能带来错误的安全感，因为它可能漏掉那些在后续运行中才会被捕获的关键漏洞。
  • 缺乏可复现性：无法复现结果，使得验证 AI 的发现、并以一致、可重复的方式信任其输出变得困难。
  • 成本与耗时增加：为了获得更完整的图景而需要多次审计，会显著增加所需的时间与计算资源。注意：对于传统软件，一旦写好，你基本可以"免费"再跑一次（不计硬件、电力等成本）。但对于重度依赖 LLM 的工具则不然——在本案中，读入一个代码库并对其推理，每次扫描可能产生数十到数百美元的 token 成本。随着当前模型迭代，这一成本未来可能下降，但更新的模型也可能更贵。

Claude Code 新的 /security-review 命令效果如何？

Anthropic 发布了一个名为 /security-review 的新命令。它设计用于在一个拉取请求（PR）上运行，检查被改动的文件并提出问题，以识别特定的安全问题。你可以在这里找到它的提示。

当我们在整个代码库上运行这个命令时，发现它识别出的安全问题相当有限。很多时候，它找不到那些当我们逐个提示 Claude Code 去搜索某一类特定安全问题时能找到的问题。

我们在 PY-APP-003、PY-APP-002 和 PY-APP-008 上运行了该命令，它只在所有应用中发现了一个 XSS，这与我们在整体实验中得到的结果大相径庭。

回答我们的问题

让我们根据所学，重新审视最初的研究问题。

  • FP/FN 率是多少？对于真实世界代码上的"原始 AI"，假阳性率非常高，最好情况是 Codex 的路径遍历 53% 或 Claude Code 的 IDOR 78%，最差情况是 Claude Code 的 SQL 注入 95%、Codex 的 SQL 注入或 IDOR 100%。按应用划分，表现也差异巨大——从 PY-APP-002（Claude Code）中 100%（10/10）的真实 IDOR，到 PY-APP-007 的 0%（0/7）。在所有应用和所有报告的问题中，Claude Code 发现了 46 个漏洞（TPR 14%、FPR 86%），Codex 报告了 21 个漏洞（TPR 18%、FPR 82%）。由于我们使用的是真实应用，本实验无法精确度量假阴性率。我们会在后续博客中介绍度量假阴性率的技术！
  • 为什么会失败？我们观察到的主要弱点是：对注入类问题的代码执行缺乏深入的语义理解。模型在过程间污点流（inter-procedural taint flow）和隐式流（implicit flows）上吃力——而这正是传统 SAST 引擎通常擅长的领域。部分局限性也来自上下文压缩（context compaction）和上下文退化（context rot）。我们会继续深入探索这些局限，并寻找缓解方案。
  • 脚手架（scaffolding）与智能体式工作流有多重要？它们不仅重要，而且正变得不可或缺。AI 在安全审查中的未来，不是单一、庞大的模型，而是一个由 AI 智能体组成的系统（包括像本案中的编程智能体），它们能使用工具、对证据进行推理，并协作发现和验证漏洞。虽然我们（尚）没有关于"带 Claude Code 访问权限的智能体"与"更典型的上下文工程（即为推理模型搭建脚手架、提供所有相关代码）"之间差异的数据，但我们观察到：系统在"走完复杂流程、并在报告安全问题途中做出有根据的决策"这一能力上，存在巨大差异。话虽如此，一个反例是 Sean Heelan 如何通过足够的上下文工程，让一个推理模型报告了一个漏洞（命中率 8%）。我们强烈建议你阅读他的博客文章。
  • 这一切的成本如何？遗憾的是，我们没能统一追踪 Claude Code 与 Codex 之间的成本。Claude Code 在所有这些漏洞、所有应用上的总成本是 114 美元（不含为非确定性测试和 /security-review 命令运行的部分）。

数据集：未来发布

我们今天不发布数据集，也不公开所分析的开源应用名称，因为我们正处于负责任的披露流程中——正在联系应用开发者，让所有安全问题得到修复和验证。一旦完成，我们才会放心地发布数据。

结论

LLM 并非明天就能取代人类安全工程师的银弹；事实上，在端到端地发现高严重性的注入式漏洞方面，它们相当薄弱。然而，它们是极其强大的工具。我们的研究表明：通过理解它们的优势（上下文推理）与弱点（对代码的深层语义），并围绕它们用先进的静态分析引擎构建复杂的智能体系统，我们能够创造出远比以往任何工具都强大得多的新一代安全工具。
