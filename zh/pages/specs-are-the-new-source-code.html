规格说明已死，规格说明万岁！

副标题：原型成了新的规格说明，而规格说明成了新的……源代码？

作者：Ravi Mehta 与 Danny Martinez · 2025 年 7 月 31 日

在我的职业生涯中，规格说明（spec）变得越来越短。我在微软刚入行时，一个产品经理（PM）的价值是用他写的规格说明的"厚度"来衡量的。多年以后，在 Tripadvisor，我们给那位把规格说明——随手写在一张餐巾纸上——带去产品评审会的 PM 封了神。产品团队常常把规格说明当成"文书工作"——开始"真正干活"（也就是把产品做出来）之前不得不做的必要之恶。工程师因优雅的代码被赞扬，设计师因漂亮的体验被称赞，PM 因做出影响力而被认可。但规格说明呢？它们往往被草草赶完、随手丢到一边、然后被遗忘。

这始终是个错误。在我的《产品经理能力工具包》中，"功能规格说明"排在最顶端——在十二项能力中名列第一——这是有原因的。它与"产品交付"和"产品质量"一起，支撑着"产品执行"。无懈可击的执行是优秀产品管理的基石，而一份出色的规格说明就是起跑线。

今天，我们的构建方式正在转变。工程师越来越快——快得多。AI 能在几分钟内把粗糙的想法变成可运行的代码。瓶颈不再是"构建"，而是"知道要构建什么"，以及"让团队围绕这些需求达成一致"。突然之间，这份不起眼的规格说明不再是转瞬即逝的文书，它是产品管理的基石——它正在变成源代码本身。

为什么产品经理突然成了瓶颈

在最近的演讲《用 AI 更快构建》中，Andrew Ng（吴恩达）指出一个前所未有的趋势：

"在我人生中，第一次有人向我建议，一个团队里产品经理的数量应该是工程师的两倍。我至今不知道这个建议是否明智，但我认为它预示了世界的方向。"——Andrew Ng

这印证了我们在上一篇文章中的预测：随着工程师借助 AI 实现数倍的产出速度，公司需要更多（而非更少）的 PM 来支持这些高产的工程师。

随着产品交付提速，产品管理的其他方方面面都承受着巨大压力——理解客户需求、打磨正确的功能、验证影响力。而所有这些压力，最终都汇聚到一个产物上——规格说明。

规格说明——新的源代码

在传统的软件开发中，程序员编写人类可读的"源代码"，它被编译成高度优化、机器可读的"目标代码"。所谓"目标代码"（也就是二进制文件）是一个可以用源代码重新生成的副产品。源代码，字面上就是"真相之源"。

来自 OpenAI 的 Sean Grove 提出了一个颇有些挑衅的论点。在他最近的演讲《新代码》中，他主张：一份写得好的提示（即规格说明）就是新的源代码。从这个角度看，我们现在的 AI 开发是倒着来的。我们精心撰写提示，向模型传达我们的意图；AI 生成代码；然后我们保留代码，却把提示丢掉了。

"这感觉就像你把源代码碎纸销毁，然后非常仔细地对二进制文件做版本控制，"Grove 观察道。

想想看。在传统编程里，源代码是神圣的。源代码包含注释、结构和文档——理解并修改系统所需的全部信息。二进制文件只是一个下游产物。但在 AI 时代，我们颠倒了这种关系。我们把生成的代码当作值得保留的产物，而把规格说明——也就是提示——当作一次性用品。Grove 认为这完全是本末倒置。代码，哪怕是优雅的代码，也只是他所说的来自规格说明的"有损投影"。就像反编译二进制文件无法还原原始的注释和变量名一样，读代码也无法告诉你它背后完整的意图。

而规格说明，则包含了一切。一份足够健壮的规格说明，能够生成"优质的 TypeScript、优质的 Rust、服务端、客户端、文档、教程、博客文章，甚至播客。"

"一份足够健壮的规格说明，能够生成优质的 TypeScript、优质的 Rust、服务端、客户端、文档、教程、博客文章，甚至播客。"——Sean Grove，OpenAI

更重要的是，规格说明能做代码做不到的事：它让人类和机器在共同的目标上达成一致。

等等，难道原型没有杀死规格说明吗？

直到最近，产品生命周期还得从规格说明（或者 PRD、概念文档、餐巾纸草图）开始，由它来启动最初的线框图、设计、原型，以及 MVP（最小可行产品）开发。

传统做法让人感觉是一种必要的恶。工程师构建基础的 MVP，只为把某个东西——任何东西——交到客户手中。"如果你的产品第一版没有让你感到难堪，那说明你发布得太晚了"成了金科玉律。

我们构建产品的整套方法最近经历了重大转变，在这个新世界里，规格说明往往是"输出"，而不是"输入"。今天，你不需要写出哪怕一行代码，就能把原型交到客户手中。像 v0、Lovable 和 Replit 这样的工具，让你在数小时内（而非数周）构建出可用的原型，且无需工程资源。

这不只是更快——它本质上是不同的。有了"氛围编程"（vibe coded）出来的原型，你可以在写下功能规格说明的第一行之前，就收集到真实的客户反馈。你可以测试假设、迭代流程、打磨交互。

旧的工作流是这样的：模糊的想法 → 线框图 → 设计 → 工程师构建的 MVP → 客户反馈 → 痛苦的规格修订 → 线框图 → 设计 → 重建 → 祈祷。

新的工作流是：模糊的想法 → 快速原型 → 客户反馈 → 清晰的规格说明 → AI 辅助的实现。

原型并没有杀死规格说明，它们让规格说明变得更好。

规格驱动的研发实践

我们来看一个具体的例子，看看这一切是怎么落地的。Danny Martinez 是 decimals 的创始人，这是一个（处于隐身期的）平台，让创作者经济领域的专家能够把其人脉网络中的人才输送进合适的岗位。

Danny 将带我们走一遍他们的"规格驱动研发"流程——这个流程带来了两个影响：

  • 对于较大的功能，与工程团队的沟通大为改善；
  • 而对于较小的功能，让毫无编程经验的 Danny 也能从详细的规格说明一路做到上线功能。

以下是 Danny 的讲述……

这是我最近做的一个例子。背景是，我们正在构建一款产品，让专家型网红能够把其网络中的候选人输送进岗位。在发布了一个新的落地页之后，我们需要给专家提供一个快速访问他们自己页面链接的方式。

我们需要在页头加一个按钮，指向 company-apply 页面。我目前正忙着邮件的事。如果方便的话，这个可以用氛围编程搞定。

这段话来自我联合创始人，指的是一个需要上线的简单按钮。足够简单，而且正是那种非技术人员现在可以自己搞定的事。

以下是这套配置，以及它如何在几分钟内上线的步骤：

  • 项目管理工具：Linear
  • IDE：VS Code
  • 扩展：GitHub Copilot Pro
  • 模型：Claude Sonnet 4
  • MCP 服务器：Linear MCP server，用于让 Linear 工单可通过 Copilot 访问

我们来看看流程中的步骤（可对照上方 Loom 视频）：

  • 从联合创始人在 Slack 上的消息生成一张 Linear 工单（00:14）
  • 在工单中明确我想要的新文案是什么（00:25）
  • 打开 Copilot，提示 Claude 打开这张 Linear 工单（01:18）
  • 提示 Claude 审阅工单，并结合代码仓库对其进行分析（01:52）
  • 提示 Claude 创建一个分支并实现这些改动（02:30）
  • 测试改动，确保按预期工作（02:52）
  • 在 GitHub 上发起一个拉取请求（PR），把这些改动合入代码仓库（03:55）
  • 等待工程师审阅 / 批准该 PR

把视角拉远，这套配置真正的威力就清晰起来了。没错，这是个微不足道的例子，但重点依然成立：一个非技术人员现在可以在 Linear 工单、代码仓库和工程师之间穿梭，而所要做的只是通过 GitHub Copilot 给 Claude 发几条提示。

再一次强调，这一切的关键部分不是代码本身，而是规格说明。

现在，有一个重要的前提需要说明，要让这套方法奏效需要满足这些条件：

  • 要具体（Being specific）：使用含糊的规格说明只会得到一团乱的代码仓库。让 Claude 先基于工单初稿、结合代码仓库审阅，并帮你把它写得更具体，是流程中必不可少的一环。在我们这里，我们也制定了写好规格说明的准则。
  • 要有选择（Being selective）：上面这套方法最适合较简单的任务。工单越复杂，就越需要懂行的人介入（在这些情况下，"自助"最终往往根本不自助）。
  • 要设关卡（Gatekeeping）：这套方法之所以好用，是因为始终有一位真正懂行的工程师在审阅改动、确保简单性与功能性之间的平衡。

但我们要说清楚：规则已经变了。规格说明是每一个构建产品的人——包括 LLM——的真相之源。

在恰当的配置下，作为一个非技术人员参与代码仓库的贡献，是完全现实的。只要有足够的时间和耐心，你就能开始理解代码仓库、并亲自实现改动，而不是每次都依赖 Claude 来救场。

也许有一天，你甚至可以一边喝着咖啡，一边期待一个 AI 智能体帮你把工单上线。

如果你是一位 PM，担心 AI 会对你的工作做什么，关键在于意识到：工作本身正在改变。但对其他人来说也一样。好消息是，优秀 PM 所需的核心技能，在这个新世界里变得更有价值。正如我们在上一篇文章中预测的，采用这种工作方式的公司，需要的 PM 会更多，而不是更少。

规格说明万岁！

科幻作家 William Gibson（发明了"赛博空间"一词）曾说：

未来已经到来——只是分布得还不均匀。

当我想到 AI 能做什么、不能做什么时，就会想起这句话。今天，AI 带来的收益极不均衡。有些事——生成代码、文本、图像——实现了量子跃迁般的进步，它们以 AI 的速度运行。而另一些事——与客户交谈、发现他们的需求、说服他们购买——仍然以人类的速度前进。

这种不均衡的分布正在重塑产品团队。聚光灯正从"实现工作"转向"理解工作"。那些始终让顶尖 PM 脱颖而出的核心技能——理解用户需求、清晰定义问题、设计优雅的解决方案——变得价值倍增。

最优秀的 PM 把这些洞察转化为规格说明——那种能对齐团队、指引实现，并在日益自动化的研发世界中作为持久产物的规格说明。
