Coding Agents 101：真正把事情做出来的艺术

Cognition 团队 ｜ 2025 年 6 月 ｜ 阅读时长约 15 分钟

现在是 2025 年。编程智能体（coding agent）并非魔法，但它们大概是我们手边最接近魔法的东西了。我们注意到，一些工程师——尤其是高级到资深（senior-to-staff）级别的——比其他人更快取得成功。在此，我们分享一些源自我们自身与客户经验的最重要的心得。

关于本指南

  • 产品无关（Product-agnostic）：我们讨论的技巧，将帮助你在任何编程智能体上取得成功。
  • 注重实战（Tactical）：我们提供最爱的、可立即行动的实用建议。
  • 技术向（Technical）：尽管编程智能体对许多人都有价值，但本指南是写给工程师看的。

开发者工具一直在快速演进。十年前，是自动补全与智能感知（IntelliSense），能够建议方法名并执行程序化的重构。四年前，是副驾驶（copilot）与 Tab 补全，能够为你写下接下来的几行代码。两年前，是生成式聊天机器人，能够辅助你的开发并为你生成整个文件。今天，是自主智能体（autonomous agent），能够把从最初描述到最终拉取请求（PR）的整个过程以极少的人为干预完成。过去两年里，我们通过构建 Devin 来专注于实现这一愿景。如今，对自主智能体的兴趣正达到新的高度，尤其是随着近期类似产品的发布1。除 Devin 之外，近期发布的产品还包括 OpenAI 的 Codex 与 Google 的 Jules。一些本地智能体，如 Cursor 和 Claude Code，可以在并行工作区中运行，以复现类似的效果。这些智能体可以呈现为多种形式，包括 Web 应用、移动应用，以及 Slack、GitHub、Linear 和 Jira 等流行工具中的集成。

虽然一个人搭配 AI 助手能做到的比任何单独的 AI 都多，但自主智能体端到端处理任务的能力，开启了一种新的多任务层次，把每一位工程师都变成了工程经理。

适应与这些新 AI 同事高效协作，需要一些时间。有趣的是，我们观察到，高级到资深级别的工程师往往最快采纳并熟练使用这些工具。最终，这些工具将在工程的所有层级变得司空见惯。基于我们的经验与客户反馈，我们希望分享关键洞见与经验教训，帮助每个人成功地将这些工具整合进自己的工作流。

开始上手（Getting Started）

提示基础（Prompting Basics）

这些基本准则将帮助你在 2025 年有效地与编程智能体交互。哪怕你别的什么都不记得，至少也应当记住这些。

说明你希望事情"怎么做"，而不只是"做什么"

把智能体看作一名初级编程搭档，它的决策可能并不可靠。简单的任务可以直接描述，但对于更复杂的任务，要从一开始就清晰地列出你偏好的做法。事先向智能体提供整体架构与逻辑，不仅能提升它成功的概率，还能减少你审查代码的时间，因为你已经熟悉了预期的方法。

示例：

与其说"添加单元测试"，不如明确要测试的功能、指出重要的边界情况，并澄清（如果有必要的话）哪些部分需要打桩（mocking）。

告诉智能体从哪里开始

想一想如果你自己来处理这个任务，会从哪里入手。即便你不知道具体的文件名或函数名，也要提及代码仓库（repository）、相关文档以及涉及的关键组件。清晰地指明这些要素，能最小化被浪费的精力与困惑。

示例：

"请为我们的代码添加对 Google 模型的支持。你应当查看最新的官方文档，并在模型组（model groups）目录中创建一个新的实现文件。"

练习防御性提示（defensive prompting）

想象一下，把同样的提示交给一名新来的实习生。哪里可能容易出现困惑或错误？预先预判这些点，并主动澄清你的指令以避免歧义。

示例：

"请修复我们搜索模块的 C++ 绑定以通过新的单元测试。要注意，每次修改代码后、在测试之前，你大概率需要重新编译这些绑定。"

授予对 CI、测试、类型系统与代码检查器（linter）的访问

智能体很大一部分的"魔法"，来自它们修复自身错误、并针对错误信息进行迭代的能力。通过类型检查器、代码检查器（Lint 工具）和单元测试这类工具提供强有力的反馈回路，能大幅提升它们的表现。考虑使用带类型的 Python 而非纯 Python，或使用 TypeScript 而非 JavaScript。教会你的智能体如何运行常见的检查与测试，确保它拥有所有必要的包与访问权限。如果智能体能与浏览器交互，请提供关于运行你前端开发环境的清晰说明。

示例：

我们的团队从主要使用无类型 Python SDK，转向了完全使用带类型的 SDK（这也是一个非常适合交给编程智能体去做的任务）。

善用你的专业知识

当你熟悉自己的代码库时，上述一切都变得更容易。即便是简单的任务，也能受益于你验证逻辑与结果的能力。人的监督仍然不可或缺——最终，你要对代码的最终正确性负责。即便这些工具变得越来越精密，所有权与验证仍将是对人类工程师至关重要的责任。

在工作流中使用智能体（Using Agents in your Workflow）

一旦你掌握了与智能体对话的基本功，就到了把这些 AI 帮手引入日常工作的时刻。以下是一些让智能体成为你日常一部分的实用方法：

立即着手处理新任务

想象一位队友给你发消息："嘿，我们能快速搭个 X 吗？"或者"我们需要微调一下 Y。"不要让它打断你的心流，只需给一个自主智能体发一条简短提示，让它去调查或做出改动。这能让你 freed 出来，保持对主要任务的专注。有个有意思的副项目想法？需要快速搭个原型、爬点数据或复现某项研究？委派给你的智能体，稍后再回来查看。

把杂活外包出去

卡在针对旧提交做二分（bisecting），或为某个新功能更新文档？把这些重复性任务交给你的智能体。你会省下宝贵的时间，并专注于更具创造性和影响力的 work。

跳过"分析 paralysis"

纠结于一次重构是否真的会简化你的代码？在两个架构方案之间无法抉择？让你的智能体把两种方案都实现出来。有了可供比较的具体示例，决策变得直截了当，而且丢弃某个方案时你也不会伤到任何人的感情。

设置预览部署（preview deployments）

把你的持续集成 / 持续部署（CI/CD）流水线配置为，在每次新建 PR 时自动创建预览部署，给你一个即时的在线 URL。在审查由 AI 智能体完成的前端任务时，这一点尤其 handy。

示例：

委派更大的任务（Intermediate：Delegating Larger Tickets）

随着你的拉取请求（PR）规模和复杂度增长到不止几个文件，想在一次 pass 中处理它们就变得有挑战了。然而，掌握如何委派中到大型任务（通常是 1–6 小时的工作量），正是自主智能体投资回报率（ROI）最高的地方。与其只节省几分钟，你可以收回数小时的生产力。较小的任务可能毫不费力，但把智能体的能力拉伸到处理更大的任务，才能带来最大的回报。

自动化你的初稿

对于实质性的任务，使用自主智能体来创建你 PR 的初稿，能启动进展并大幅削减你的工作量。这里的成功取决于事先清晰地沟通你期望的做法。把自己想象成指导初级开发者的架构师。清晰、详细的指令，有助于避免把不必要的时间花在纠正智能体代码中的根本性误解上。

领域类比：起草与打磨

领域起草（Drafting）打磨（Refining）
新闻业记者收集初始信息，写出文章初稿。编辑审阅草稿，进行事实核查、润色，并最终定稿发布。
餐饮业线厨（line cook）准备食材并制作初步菜品。副厨（sous chef）加入调味料并调整菜品以使其更美味，然后才送到食客面前。
编程自主智能体基于初始计划启动任务，并创建出初稿方案。人类开发者审查初稿 PR，给出反馈，并在合并前添加人工打磨。

🛑 请记住，大型任务还不是完全"免动手"的（至少目前如此）。对于更具挑战性的任务，要预期会有多轮反馈循环，并预见到需要一些人工打磨来润色。一个现实的目标大约是节省 80% 的时间，而非完全自动化，你的专业知识对于验证与最终质量保障仍然至关重要。

共同开发一份 PRD

对于复杂或定义模糊的任务，与你的自主智能体协作创建一份详细计划可能极为有效。即便你一开始并不知道每一个细微差别或需求，也没关系。先提示你的智能体去探索一些发现式的问题，比如"我们的认证系统是如何运作的？"或"哪些服务可能受到影响？"你也可以让智能体为你识别出具体的、相关的代码目标，以便尽早确认。

某些智能体，例如 Devin 和 Claude Code，提供了专门的规划模式（planning modes），专注于阅读与探索现有代码，而不是立即修改它。如果你偏好在委派任务前做更深入的准备，像 deepwiki.com 和 Devin Search 这样的专用代码库搜索工具，可以快速提供关于你代码库的洞察，帮助简化这一过程。

设置检查点（checkpoints）

对于多部分任务，尤其是那些涉及多个代码库的任务，要在过程中设立清晰的检查点：

计划 → 实现一块 → 测试 → 修复 → 检查点审查 → 下一块

在每个重要阶段之后显式地要求暂停，特别是对于跨多层（例如数据库、后端、前端）构建的复杂功能。利用这些检查点来确保实现符合你的预期、澄清疑问（例如"解释一下认证流程并确认其安全性"），并尽早纠正方向，以避免连锁（cascading）问题。

示例：

"我希望你实现这个功能，它将横跨我们的数据库、后端和多个前端界面。请先规划出所需的数据库 schema 变更，完成后告诉我，以便我应用迁移。" → "现在请实现后端变更，并添加测试以确保 XYZ 工作正常。完成后告诉我。" → "现在请在咱们的 Web 和移动两个界面中都实现改动，以调用新的后端端点。"

教会它验证自己的工作

在给出反馈时，不要仅仅指出问题（"这个函数不工作"）。清晰地阐明你的测试流程，让智能体能够独立验证未来的任务。对于你会频繁重复的测试模式，把这些整合进智能体的永久知识库（参见"添加到你的智能体知识库"）。

示例：

在 Devin 中，我们主动提示用户将必要的测试流程保存到智能体的持续记忆中，从而简化未来的交互。

在 AI 热点区提高测试覆盖率

目前，智能体还无法充分交互式地彻底测试所有场景。在那些被 AI 大量修改的区域增强测试覆盖率，能让你对智能体的输出更有信心。扎实的测试意味着，看起来正确的代码可以放心地合并，无需担忧。

自动化工作流（Advanced：Automating Workflows）

智能体响应 incoming 事件的速度比人类快得多，而且比起人类 counterpart，它们更愿意去做那些无聊、重复的工作。

为你最重复的工作创建快捷方式

工程团队经常会遇到重复性的、例行性的任务。这些都是用智能体实现自动化的绝佳候选。常见的例子包括：

  • 功能开关（feature flag）移除
  • 依赖项升级
  • 在新的功能 PR 上修复并补充测试

为了高效地搭建这套流程，一位有经验的工程师通常会创建一个健壮、可复用的提示模板2。在 Devin 中，这些被称为 playbook（实战手册），可以针对这些场景反复运行。

智能代码审查与强制约束（Intelligent Code Review & Enforcement）

虽然存在用于快速代码审查的专用工具3（例如 Greptile 和 CodeRabbit），但自主智能体可以成为一个有意思的选项，提供更准确的洞察，尤其是当它们已经为你的代码仓库的功能建立过索引时。

示例：

在 Cognition，我们喜欢维护一份工程师最常犯错误的清单，并把这份清单提交进代码库。然后，我们不再去编写经典的 lint 规则来捕获这些错误（这通常并不可行），而是让一个智能体在每一个新 PR 上运行，以检查这些错误。

接入事故与告警

你还可以设置自主智能体，以响应特定事件的方式自动触发。例如，Devin 提供了一个易用的 API，其他智能体也可以通过 CLI 命令集成进自定义工作流。这些设置与 MCP 配合尤其好，可以接入第三方的错误日志。

⚠️ 当涉及到对生产服务的事故做分诊（triage）时，AI 的调试技能并不那么出色。与其让 AI 来端到端地修复随问题出现的缺陷，往往更务实的做法是让 AI 仅仅标记出最可疑的错误、变更等。

定制与性能提升（Customization & Improving Performance）

环境搭建（Environment Setup）

添加到你的智能体知识库

如果你的智能体犯了某些常见错误，那正是把你的反馈沉淀进智能体知识库的好时机。在 Devin 中，有一套专门的知识管理系统。许多产品提供 .rules 文件、.md 文件，供智能体永久吸收。不要只给它关于你所用框架的指南，还要告诉它你的项目的整体架构。告诉它不同类型的任务通常采用什么测试、如何运行重要命令，以及你推荐使用哪些工具。

实践考量（Practical Considerations）

自主智能体的局限性

有限的调试技能

缺陷报告可能具有欺骗性的简单。但许多缺陷往往不仅需要访问数据库和日志，还需要超越当今大多数 AI 智能体的调试水平。如果使用 AI 来辅助调试，我们建议让它提供一份可能根本原因（root causes）的清单，而不是试图让它自己调试并修复一切。然后，人类可以根据自身经验判断哪一个是真正的根本原因。不过，一旦原因已知，智能体在实现修复方面仍然可以很有帮助。

粗糙的细粒度视觉推理能力

总体而言，今天的模型在匹配设计稿截图或 Figma 模型所需的细节层次上，视觉推理能力并不出色。它们在可以用代码层次描述的视觉内容上最可靠（例如，把代码从 Figma 交给它）。如果你想让它匹配你的视觉风格，应当使用一个带有可复用组件的良好设计系统。

知识截止（Knowledge Cutoffs）

每当你想使用一个新的库时，都应当明确地把它指向最新的官方文档。否则，由于预训练基础模型中的知识截止，大多数智能体会假设这些库的旧有模式。一个好的智能体如果你把它指向文档，是可以克服这一点的，但你必须对此保持觉察（请记住，智能体甚至不知道这些库已经有了新版本）。

管理时间与减少损失

并非你每次使用智能体都会成功。在 2025 年，这些智能体的结果确实存在一定程度的差异。工作的一部分，就是学会如何使用智能体，以最大化遇到成功结果的概率，同时最小化浪费的时间和 Token。

更早地愿意及时止损

刚接触智能体的人常犯的一个错误是，即便智能体的工作已经偏离轨道，也要硬着头皮把它这次交互做成。如果你发现自己想着"它在无视我的指令"或"这东西在兜圈子"，你就应该可以接受中止那段对话或手动接管。发送更多消息，更可能说明你的任务内在复杂度高于智能体的能力，而非某个可以被纠正的简单错误。

让你的实验多样化

如果你刚接触与智能体协作，我们建议一开始就把赌注分散。尝试一系列不同的提示和想法。在智能体自然表现出色的任务类型上加倍下注——并在它们不擅长的那些上及时止损。不要觉得有必要强迫你的智能体每次都成功。

当没有进展时，从头开始

与和人类协作相比，在智能体上，从头开始是正确答案的情况要频繁得多。如果你给了一个智能体任务，而它在应对反馈或纠正方向上苦苦挣扎，那么带着全部指令、用一个全新的智能体重新开始，往往能更快地走向成功。智能体修复一个被搞乱的环境的能力，远不如它从零开始吐出新鲜代码的能力。

安全与权限（Security and Permissioning）

为你的智能体创建账户

一个临时邮箱（throwaway email）有助于安全地测试网站。如果智能体需要访问云资源，为它创建自定义的 IAM 角色。

给它一个开发 / 预发（staging）环境

理想情况下，智能体使用与你的团队工程师相同的测试设置。我们建议完全避免授予对生产服务的访问。在使用远程智能体时，你可以在智能体的远程机器上运行完全隔离的测试环境。

只读 API 密钥

在可能的情况下，给它只读（readonly）访问权限。我们发现，由人类手动运行任何与外部服务交互的脚本仍然是有帮助的。

重大变革在前方（Big Changes Ahead）

我们坚信，软件工程师不会无处可去。即便编程智能体变得更聪明、更有能力，深厚的技术专长与对你的代码库的亲切认知仍然无比宝贵。对你项目、系统和代码真正的所有权，如今比以往任何时候都更关键。在今天我们的团队中，工程师被期望在 oversight 多个系统的同时，仍保持深刻的理解与审慎的判断。随着自动化放大了你的影响力，同时 juggle 并行任务的能力将不仅变得可能；它将变得必不可少。我们很高兴能分享在为我们自己的组织准备这场转变时所收集的洞见，好让你和你的团队也能在不断演进的软件开发世界中茁壮成长。
